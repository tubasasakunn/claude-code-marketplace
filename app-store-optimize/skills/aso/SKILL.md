# ASO プレイブック（調査 → 文言 → 画像 → 計測）

`/swift-app:release-assets` が「素材をどう作るか（手順）」なら、このスキルは
「何を書き・何を見せるか（中身）」を決める。フィールドの文字数上限・
ファイル配置・CI 反映は `release/README.md` と `/swift-app:release-assets` が正本。
アプリ固有値は `appstore.config.json`。

作業は必ず **Phase 1（調査）→ Phase 2（文言）→ Phase 3（画像）→ Phase 4（計測）**
の順。調査を飛ばして文言をいじらない（感覚で選んだ語は検証できない）。

---

## 前提知識：App Store の索引と重み

- 検索索引の対象は **アプリ名 > サブタイトル > キーワード欄**（この順に重い）。
  近年は**スクショのキャプション文字も OCR で索引される**ため、画像の見出し語も
  検索語として扱う。説明文（description）は**検索順位に効かない**が CVR に効く。
- Apple は**フィールドを横断して語を組み合わせて索引する**。
  「時間 + 記録」がタイトルとサブタイトルに分かれていても「時間記録」でヒットする。
  したがって**同じ語を複数フィールドに入れるのは純粋な無駄**（1 回しか数えない）。
- 順位はテキスト適合だけでなく、**タップ率（TTR）・CVR・DL 数・評価・
  リテンション**の複合。文言だけで上げ切れない分は Phase 3・4 で取りに行く。

## Phase 1：調査

調査結果は `release/aso/` に Markdown で残す（例：`release/aso/2026-07-research.md`）。
次回の見直しで「前回どの語を、どの根拠で選んだか」を diff できるようにする。

### 1-1. 候補キーワードの洗い出し（4 つの源泉）

| 源泉 | やり方 |
|---|---|
| コンセプト分解 | アプリの機能語・ベネフィット語・悩み語・利用シーン語を列挙（仕様書・CLAUDE.md セクション 1 から） |
| 競合メタデータ | 上位競合 3〜5 本のタイトル・サブタイトルから頻出語を抽出（下の iTunes Search API） |
| ストアのサジェスト | App Store 検索窓に主要語を入れたときの補完候補（実機/WebSearch で「App Store <語> サジェスト」） |
| レビュー語彙 | 自アプリ・競合のレビューでユーザーが実際に使う言い回しを拾う（機能名ではなく悩み・目的の表現） |

### 1-2. 競合・順位の実査（iTunes Search API）

キー不要・無認証で使える。**country=jp を忘れない**（人気度・順位は国別）。

```bash
# 検索語 → 上位アプリ（= その語の競合と自分の順位）
curl -s "https://itunes.apple.com/search?term=<キーワード>&country=jp&entity=software&limit=20" \
  | python3 -c "import json,sys; [print(i+1, r['trackName'], '|', r.get('genres',[''])[0]) for i,r in enumerate(json.load(sys.stdin)['results'])]"

# 競合 1 本の詳細（説明文・ジャンル・評価数）
curl -s "https://itunes.apple.com/lookup?id=<trackId>&country=jp" | python3 -m json.tool
```

各候補語について記録する： **検索結果の上位が何か／自アプリの現在順位／
上位の評価数規模（勝てる土俵か）**。上位が全部 10 万評価級なら短尾語は捨て、
長尾（2〜3 語の複合）へ逃がす。

### 1-3. 評価軸と選定

各候補語を **関連度 × 検索ボリューム ÷ 競合強度** で並べる。ボリュームの実数は
無料では取れないので、サジェストに出るか・上位アプリの評価数・Apple Search Ads の
人気度（使える場合）を代理指標にする。原則：

- **関連度が最優先**。関連の薄い人気語で瞬間的に露出しても CVR とリテンションが
  下がり、結局順位が落ちる。
- 新規・小規模アプリは**長尾から**。短尾の一般語はブランドが育ってから。
- 「勝ち筋の語 10〜20 個」まで絞り、タイトル / サブタイトル / キーワード欄 /
  スクショ見出しに**重複なく**割り付ける（Phase 2・3）。

### 1-4. 日本語特有の注意（primary_locale=ja の場合）

- **漢字・ひらがな・カタカナは別トークン**として索引される。主要語の
  読み・別表記（例：「時間」→「じかん」、「カメラ」→「かめら」）は
  キーワード欄で拾う。ユーザーはひらがなで打ちかけのまま検索することが多い。
- 送り仮名・長音・拗音の表記ゆれ（「サーバー/サーバ」）も同様に別語扱い。
- 複合語の区切りにも敏感。狙う複合語はどこかのフィールドに**その形のまま**入れる。

## Phase 2：文言（メタデータ設計）

`release/<version>/` の各 .txt に落とす。編集したら必ず
`python3 scripts/check_release_metadata.py <version>` で PASS を確認（/swift-app:release-assets 参照）。

### フィールド別の設計指針

| フィールド | 上限 | 役割と書き方 |
|---|---|---|
| `app_name` | 30 | **ブランド名＋最重要キーワード 1 軸**。「<名前>-<最重要語のタグライン>」形式が定石。索引の重みが最大なので、勝ちたい語はここ。 |
| `subtitle` | 30 | **タイトルとは別軸の検索語＋ベネフィット**。検索結果でタイトル直下に見えるため、索引と CVR の両方を担う。タイトルの語を繰り返さない。 |
| `keywords` | 100 | 索引専用（ユーザーには見えない）。**半角カンマ区切り・カンマ後に空白なし**。タイトル/サブタイトルの語・アプリ名・カテゴリ名は入れない（重複は無駄）。読み・類義語・表記ゆれ・関連語で埋める。単数/複数はどちらか一方。競合ブランド名は入れない（2.3.7）。 |
| `description` | 4000 | 検索順位には効かない。**折りたたみ前の冒頭 1〜3 行が勝負**：コンセプト＋差別化＋誰の何を解決するか。以降は機能を見出し的に列挙（スクロールで拾い読みされる前提）。最後にサポート導線。 |
| `promotional_text` | 170 | **審査なしで随時更新できる唯一のテキスト**。季節訴求・新機能ハイライト・キャンペーンの実験枠として使う。恒常的な説明を置かない。 |
| `whats_new` | 4000 | 更新内容を具体的に。「バグ修正と改善」だけにしない（継続開発のシグナルであり、既存ユーザーへの再訴求枠）。 |

### コンプライアンス（App Review 2.3 系）

- 競合ブランド名・他社商標をどのフィールドにも入れない（2.3.7）。
- 価格表現（「無料」「セール」等）をアプリ名・サブタイトル・アイコンに入れない（2.3.7）。
- 説明・スクショが実機能と乖離しない（2.3.1）。誇大な最上級表現は避ける。

### 割り付けの最終チェック

Phase 1 で選んだ語の割り付け表を調査メモに残し、以下を機械的に確認する：

- [ ] 同じ語が 2 フィールド以上に出ていない（活用形・単複違いも含む）
- [ ] 最重要語がタイトルに、次点の別軸語がサブタイトルにある
- [ ] keywords に空白・全角カンマ・読点が混ざっていない
- [ ] 狙う複合語がどこかに「その形のまま」存在する
- [ ] `check_release_metadata.py` が PASS

## Phase 3：画像（スクショ・アイコン）

生成の実務（`material/` → `scripts/make_store_images.py` → `img/`、サイズ厳守）は
`/swift-app:release-assets`。ここでは**構成とコピーの決め方**。構成は `scripts/store_slides.json`。

### スクショの設計原則

- **最初の 1〜3 枚がほぼ全て**。検索結果に露出するのは先頭 1〜3 枚で、
  大半のユーザーは 3 枚目以降を見ない。1 枚目 = コンセプト（タグライン＋
  コア画面）、2〜3 枚目 = コア体験。以降に補助機能・信頼要素（プライバシー等）。
  このテンプレートの定石順：**コンセプト → コア操作 → 低コストの入力 →
  振り返り → プライバシー**。
- **キャプションは 3〜5 語**、「動詞＋ベネフィット」型（機能名の羅列にしない）。
  例：「開いて 3 秒で記録」＞「タイマー機能」。
- **キャプションは OCR で検索索引される**。Phase 1 の割り付け表から
  「メタデータに入り切らなかった準主要語」をスクショ見出しに配置する。
- 縦向き・実 UI を含める（モック単体や実機能にない画面は 2.3.3 違反リスク）。
  高コントラスト・大きな文字。ブランド色は `appstore.config.json` の `brand` と揃える。
- 競合上位 3〜5 本のスクショ 1 枚目を並べて見る（Phase 1 の実査で trackViewUrl を
  控えておく）。**カテゴリの視覚的慣習に沿いつつ、1 枚目の主張だけ差別化**する。

### アイコン

- 小サイズ（検索結果の並び）で判別できる**単一モチーフ＋単一背景色**。文字を入れない。
- カテゴリ上位と並べたとき「同じ棚の商品に見えて、色で見分けられる」のが理想。

### App Preview（動画・任意）

- 最初の 3 秒にコア体験。無音再生前提。実機画面キャプチャのみ（実写・手の映り込み不可）。
- 効果が出るのは操作感が価値のアプリ。静止画で伝わるアプリでは無理に作らない。

## Phase 4：計測と反復

ASO は一回きりではなくループ。**4〜6 週間サイクル**で見直す。

1. **定点観測**：主要 10〜20 語の順位を iTunes Search API で記録し、
   調査メモ（`release/aso/`）に追記する。DL 数・インプレッションは
   App Analytics（または harness の ASC レポート API：CLAUDE.md セクション 11）。
2. **ファネルで診断**：
   - 検索順位が低い → Phase 1・2（語の選定・割り付け）を見直す
   - 表示は多いがタップされない → アイコン・タイトル・スクショ 1 枚目
   - ページは見られるが DL されない → スクショ 2 枚目以降・説明文冒頭・評価
3. **A/B テスト**：App Store Connect の Product Page Optimization（PPO）で
   アイコン・スクショ・プレビューを最大 3 バリアント試せる（文言は対象外）。
   広告・SNS 流入がある場合は Custom Product Pages で流入元別の訴求を分ける。
4. **promotional_text を実験枠に**：審査なしで変えられるので、
   訴求コピーの仮説検証はまずここで回す。
5. **評価・レビュー**：評価は順位と CVR の両方に効く。依頼は
   「価値を体感した直後」（タスク完了・継続 N 日目）に `SKStoreReviewController` で。
   低評価レビューの語彙は次サイクルの Phase 1 の入力にする。

### 変更時の運用ルール

- 文言・画像の変更は**一度に 1 軸**（キーワード欄だけ、スクショだけ）に絞ると
  効果の因果が読める。全とっかえは初回リリース時のみ。
- 変更前のメタデータは git 履歴で追えるので、調査メモには
  「何を・なぜ・何を期待して」変えたかだけ書く。
- 反映は main マージで CI が自動実行（`release/README.md`）。キーワード欄と
  スクショの変更は**新バージョンの審査が必要**（promotional_text のみ即時）。

## 罠

- 人気語を関連度無視で詰めると、露出は増えても CVR・リテンションが下がり
  中期的に順位が落ちる。関連度 > ボリューム。
- キーワード欄の重複（タイトルと同じ語・単複両方・アプリ名）は 100 文字の純損失。
- 順位・人気度は**国別**。country=jp を付け忘れた調査結果で判断しない。
- 日本語はひらがな/カタカナ/漢字が別トークン。読みを入れ忘れると
  「打ちかけ検索」を全部取りこぼす。
- スクショの見出しをメタデータと矛盾させない（subtitle と違う訴求軸を名乗る等）。
- 説明文にキーワードを詰めない。iOS では検索に効かず、読みにくさで CVR だけ落ちる。
