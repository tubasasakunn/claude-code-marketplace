# 踏んだ罠

実装中に実際に壊れたものだけを書く。**どれも一度は踏む**ので、作り始める前に目を通すとよい。

---

## 端末モックの四隅検出

画面の四隅さえ取れれば射影変換で流し込めるが、その四隅を取るところで 3 回壊れた。

### 辺を角度順に並べると、対辺どうしが隣り合う

長方形の 4 辺は 2 組の平行辺なので、**角度でソートすると対辺が隣接する**。
その 2 直線の交点はほぼ無限遠で、座標が `-120518` のような値になる。

→ **凸包上の順序**（空間的に隣り合う順）で並べてから交点を取る。

### 1px の揺れで、まっすぐな辺が複数に割れる

書き出しのアンチエイリアスで輪郭が 1px 揺れる（`x=291` と `x=292` を行き来する）。
凸包は厳密なので、直線 1 辺が短い辺 3 本に分断される。すると「長い順に 4 本」で対辺が混ざる。

→ 連続する辺を**向きでまとめて**から選ぶ。角丸の弧も 1 つの塊にまとまるが、
そちらは直線に乗らないので**残差で弾ける**。残った塊に最小二乗で直線を当てる。

### 寝かせたモックで画面の縦横が入れ替わる

「画像座標で左上の点から時計回り」に並べると、端末が寝ているモックでは
画像上の左上が画面の左上とは限らない。スクリーンショットの幅と高さが入れ替わり、
**中身が 90 度倒れて入る**。

→ 画面は必ず縦長なので、**短辺が幅に来るまで巡回**させる。残る 180 度の曖昧さは
**ノッチ**（画面の中でマスクが抜けている穴）が上辺の側に来る向きで決める。

## 射影のずれ

### 端末の縁から背景が透ける

四隅にぴったり合わせると、丸め誤差 1px 分だけ画面の縁から地の色が覗く
（オレンジの背景に細い輪郭線が出た）。

→ 四隅を**中心から 0.6% 外へ広げる**。はみ出した分はフレームのベゼルが隠すので、
広げる側に倒すのが安全。

### 端末の四隅に白い三角が出る

スクリーンショットは矩形なので、モックの角丸からはみ出す。背景が明るい画面
（カレンダーなど）だと、そこが白い三角として覗く。

→ `.mock-shot` に**実機と同じだけの角丸**を入れる。縦横比 1:2.17 なので水平/垂直を
別指定する（`border-radius: 14% / 6.4%`）。

### プレビューの zoom で変形が二重に縮む

`getBoundingClientRect()` は zoom 後の実寸を返すため、`?preview=1` のときだけ
変形が二重に縮んで端末が小さくなる。

→ **`offsetWidth` / `offsetHeight`** を使う。zoom の影響を受けない CSS px が取れる。

## 配置

### 縦キャンバスで 2 台を横に並べると、端末は高さの 56% しか使えない

幅 1320 に 2 台入れると、矢印の隙間を確保した時点で画面は 350px / 560px が上限。
要素の高さ＝w なので大きい方でも高さ 1300 しか使わず、**見出しとの間に 700px 以上の
空白が残る**。埋めようと大きくすると画面を左右に 2 割以上切ることになる。

→ 縦で 2 台やるなら**対角か階段状にずらす**。横幅を取り合わなくなるので、それぞれ
キャンバス幅を使える。矢印も読みの流れ（左上 → 右下）と一致する。

### 回転させると 2 台が近づく

`rotate` を掛けると見かけの幅が広がるので、座標上は 180px 空けたつもりでも
実際は 78px しか空かない。矢印を通す隙間が消える。

→ 回転後のバウンディングボックスで考える。幅は
`w·cos θ + h·sin θ`、高さは `w·sin θ + h·cos θ` に広がる。
→ 目標値: **矢印を通すなら隙間は 200px 前後**（頭だけで 50〜60px 使う）。

### つなぎで片方にベゼルしか映らない

「またぎキャンバスの中央に置けば半分ずつ入る」と思うと外す。合わせるのは
**モック画像の中心ではなく画面の中心**。

→ `iphone-tilt` は画像 1024 の中で画面が `x=99.7〜913`（中心 506.3）にある。
表示幅 2500（2.441 倍）なら画面の中心は `x + 1236`。ここから逆算して置く。

`iphone-flat` は画面がほぼ画像の中央にある（中心 516.5, 511.5 ≒ 512, 512）ので、
**回転させても画面の中心は要素の中心とほぼ一致する**。こちらは `x + w/2` で置ける。

### つなぎの片割れを「単体で弱い」と直しにいかない

1 枚ずつ眺めると、つなぎの 2 枚目は「見出し＋画面の一部」で薄く見える。しかし
**ストア画像が 1 枚だけ単独で見られる場面は無い**（検索結果は 3 枚並び、詳細ページは
前後が見える横スクロール）。薄さを埋めようと要素を足すと、3 枚並びの流れが濁る。

→ 判断は `tools/preview.mjs` の**検索結果ビュー**で行う。

### 傾いたモックのつなぎは「画面の中心」では決まらない

`iphone-flat` は画面中心＝要素中心なので中心合わせでよいが、**tilt / lay はせん断が
ある**ので、画面中心を切れ目に置いても、見せたいものが片方に寄る（実際、顔が
2 枚目にほとんど入らなかった）。

→ **見せたいものがある高さ `v` を固定し、その高さでの画面左右端に対する切れ目の
割合**で解く。「v≈0.30 の高さで 55:45 にしたい」から x を逆算する。

### つなぎは「中心を合わせる」だけでは決まらない

画面の中心を切れ目に置くのは出発点でしかない。実際に効くのは
**切れ目に何を跨がせないか**を先に列挙して、そこから倍率と位置を解くこと。

四隅から、スクリーンショット内の相対位置 `(u, v)` がキャンバスのどこに来るかは

```
P(u,v) ≒ TL + u·(TR − TL) + v·(BL − TL)
```

で出る。「夕日 `(0.494, 0.575)` は 1 枚目に完全に入れる」「日付 `(0.5, 0.905)` も
1 枚目」「共有アイコン `(0.89, 0.91)` は切れ目で割らない」を連立すると倍率の下限が出る。

**傾きのあるモックには倍率で解けない制約がある。** `iphone-tilt`（23°）では、画面の
右辺がキャンバス高さ 2868px を下るあいだに **1188px 左へ流れる（倍率に依らない定数）**。
つまり夕日を 1 枚目に置く限り、2 枚目の右下は必ず端末の側面になる。倍率をいじり続けても
解けないので、早めに「側面に光を当てる」等の別解へ切り替える。

### 回転方向で、つなぎの 1 枚目に入る量が変わる

左回りだと左上の角が張り出して端末の上部が入り、右回りだと左下の角が張り出して
下部だけが入る。**同じ角度でも見え方が変わる**ので、方向を変えたら位置も調整する。

### 端末を大きくすると、下の UI が中途半端に切れる

タブバーの上半分だけが残るような切れ方が一番見苦しい。

→ 切るなら**完全に画面外へ抜く**。中途半端に残さない。

### 全枚で端末位置を揃えると、切り口が全画面の共通解になる（上へ抜く場合も同じ）

「日々が同じ場所に積もる」ように端末を全枚で揃える構成にすると、下端の切り口は
**すべての画面の UI 配置を同時に満たす 1 つの値**になる。実測したら通る帯が
**19px（84.40%〜85.24%）しか無かった**という例がある。84.1% ではショートの
シャッフルボタンが真っ二つ、85.8% では撮影画面の隅の照準が青い破片になって残る。

→ **各画面の UI の位置を先に実測してから y を決める**（numpy で 10 行）。
   **上へ抜く場合も同じ。** 上へ 34% 抜いた例では、5 画面すべてを通る切り口が
   元画像 y=882（設定画面のカード下端 869 とセクションラベル 965 の 96px の隙間）
   しか無かった。
→ 判断のコツ: **抜く側の要素には余白が要らない**（画面外に落ちるだけ）ので、
   切り口は上限側に寄せて、残す側の余裕を稼ぐ。

### 切り出した UI 片を「元の少し横」に置くと、同じものが 2 つあるように見える

breakout は元の要素が画面にも残っているので、隣に置くと複製に見える。

→ **元の要素を完全に覆う位置に、はっきり大きい倍率で重ねる**。
   「拡大して手前に持ち上げた」と読ませる。

### 板の「中身」と「覆う範囲」は別々の帯に落とす

切り出した板には縁が 2 つある。**中身の下端**は 1.0 倍で下がるが、**板が覆い隠す
範囲の下端**は表示倍率ぶん下がる。片方だけ帯に落としても、もう片方が UI を割る。

外すと「板の中でボタンが割れる」か「板の外にボタンのにじみが覗く」のどちらかが必ず起きる。
両立するまで板の上端を空き帯 2 つぶん動かすことになる。`tools/measure_bands.py` で
先に帯を出し、**両方の縁が帯に入る位置**を探す。

### 要素が詰まった画面には、その板は置けない

設定画面のように行間が詰まっていると、どう動かしても縁がどこかを削る。
**矩形の方を削って、画面側に残す**のが正解。板に全部入れようとしない。

### 覆うのは切り出した要素だけでは足りない

板を置いたら、**隣の別の UI が板の縁で割れた**（共有アイコンが縦に切れ、進捗バーの
左端だけが白い破片で残る）。切るときと同じ話で、中途半端に残るのがいちばん見苦しい。

→ **板の縁に別の UI を半分だけ残さない。覆うなら周辺ごと全部。**

### 軸の合った長方形は「浮かず」に画面の一部に見える

全幅の UI（タブバーなど）を切り出して左右キャンバス外まで広げたら、端末の下端が
板で塞がって輪郭が消え、**板が単なる帯**になった。全幅の要素は倍率を稼げないので、
「手前に持ち上げた」と読ませる手掛かりが無くなる。

→ ① 矩形を上へ広げて板を縦長にする ② 1〜2° 傾ける ③ 板の左右に画面のふちを 40px 残す。

## 描画

### 矢印が黒い塊になる

CSS で `.arrow path { fill: ... }` とすると**線の path にも fill が当たり**、
曲線とその弦で囲まれた面が塗り潰される。

→ 線と頭で**クラスを分ける**。`.line { fill: none }` / `.tip { stroke: none }`。

### 和文の蛍光ペンは掛ける高さを間違えると読めない

`<mark>` に `linear-gradient(transparent 56%, ...)` を掛けると、欧文では
それらしく見えても**和文は横画が塗り潰されて読めなくなる**。

→ 和文は **62%〜98%** あたりに掛ける。サンプルは色替え（`<em>`）しか使っていないので、
   蛍光ペンを選ぶと一度は自分で失敗する。

### 暗い地では ☑ のチェックが見えない

`base.css` のチェックは data URI の SVG で、`stroke='%23000'` が直書きされている。
`currentColor` は data URI 内で解決されないので、暗い地のテンプレートでは
**チェックだけが消えて「空の枠」に見える**。

→ 暗い地なら `style.css` で `.checklist li::before { background-image: ... }` を
白ストロークの data URI に差し替える。

### `.mock:nth-of-type(n)` で個別指定はできない

`nth-of-type` はタグ名で数えるが、`compose.js` は `.wordmark`（同じ div）を mock より
前に置く。**ワードマークの有無で番号がずれる**ので、枚ごとに影や filter が入れ替わる。

→ 個別に効かせたいものは `variant` のクラス（`.v-<名前> .mock`）で分ける。

### バッジは見出しやサブより手前に出る

`.badge` は `z-index: 5` で `.head`（4）より上。右上に置くと**サブコピーの末尾を
黙って隠す**。文字が途中で切れているようにしか見えず、原因を探すのに時間がかかる。

### チェックマークに絵文字を使うと崩れる

`☑` は環境で字形が変わるうえ、線の太さを見出しに合わせられない。

→ 枠は CSS で描き、中のチェックだけ SVG の data URI にする。

## 書き出し

### 非同期の合成が終わる前に撮ってしまう

モックへの流し込みも切り出しも、画像の実寸が要るので非同期。画像の `complete` を
待つだけでは足りない。

→ テンプレートが `window.__ready`（Promise）を公開し、書き出し側がそれを待つ。

### Playwright のバージョンとブラウザが噛み合わない

新しい版を入れると別ビルドのブラウザを要求し、キャッシュがあっても再ダウンロードになる。

→ **キャッシュ済みのブラウザに合うバージョンに固定**する（`~/Library/Caches/ms-playwright/` を見る）。

### エディタをサーバー越しに開くと画像が全滅する

`content.js` の画像パスがリポジトリの外（`../../apps/...`）を指していると、
配信ルートより上に出られず 404 になる。`file://` では動くので気づきにくい。

→ 配信の基点を**素材が入る範囲まで上げる**。

## 素材

### 白い面で矩形を測ると、カードの下端が上にずれる

`measure_cards.py` は「ほぼ白」の行で帯を拾うので、カード下部の細い文字が並ぶ行で
判定が落ちる。そのまま切り出すと**文字が切れる**。

→ 出た値はカードの実際の下端まで少し広げてから使う。

### 素材に開発用の UI が写っていることがある

Debug ビルドで撮った素材には「開発用スキップ」ボタンや「MOCK MODE」バッジが
入っていることがある。**そのままではストア画像に使えない**（審査でも落ちうる）。

→ 使う前に**全点を並べて一度目で見る**。該当する画面は避けるか、撮り直す。

### 情報密度の低い画面は、縮小すると白紙に見える

「どの枚も画面に何が映っているか判別できる」は端末の大きさだけでは決まらない。
要素の少ない画面（入力待ちの画面など）は、サムネイルでは白い板になる。

→ **密度の低い画面を小さい方の端末に置かない。** 2 台構成なら大きい側に回す。

### LP 用に縮小した画像を使うと甘くなる

620px 幅の画像を端末モックの画面（1000px 超）に引き伸ばすと、UI の細線が潰れる。

→ シミュレータから撮った原寸を使う。

### 「完成版は低解像度、原寸は単色」で詰まる

動画・カメラ系のアプリでは、原寸のスクリーンショットは映像領域が単色（純緑など）で
塗られていて、中身が入った完成版は LP 用に縮小されている、という 2 系統になりがち。
どちらもそのままでは使えない。

→ **原寸に素材を流し込んで作り直す**（`tools/fill_chroma.py`）。置き換えではなく
   アンコンポジットするので、単色の上に乗った半透明の UI が潰れない。
   別々に走らせた 3 体が全員この道を選んだ。

### モーダルシートの画面は、上に暗転帯と角丸が写る

シート表示の画面をスクリーンショットに撮ると、背後のビューの暗転帯とシートの
角丸が一緒に入る。**事前にクロップして直すことはできない**——モックは画像全体を
画面の四角形へ引き伸ばすので、切ると縦に伸びる。

→ 帯ごと出すか、**暗転帯の色をシートの地色にブレンドで寄せて全画面に見せる**。
   縦横比を保ったまま消せるので、こちらの方が使える場面が多い（`fill_chroma.py` と
   同じ発想で、色を置き換えるだけ。ステータスバーと Dynamic Island は残す）。

### フレームの内縁にキー色のハロが残る

`prep_mockup.py` の初版は、抜く閾値（`soft > 0.08`）に届いた画素にしかデスピルを
掛けていなかった。そのため**アルファは 255 のまま色だけキー色に汚染された画素**が
内縁に数千 px 残り、暗い映像を流し込むと画面の輪郭に沿ってオリーブの 1px 線が出た。

汚染は暗く落ちている（`rgb(27,31,0)` など）ので、純色との距離では「遠い色」と
判定されて素通りする。

→ 閾値と無関係に**全画素からキー色の寄与を引く**（アンコンポジット）。
   キー色と無関係な色は寄与 0 になるので、黒・シルバー・肌色は影響を受けない。
   **修正済み**だが、自分でモックを作り直すときは同じ罠がある。
