# ストア画像を HTML で組んで書き出す (screenshot-build)

## これは何か

ストア画像を **HTML + CSS で組み、Playwright で PNG に書き出す**ための道具とサンプル。
Figma も Photoshop も要らない。

`screenshot-crafting` が「何を訴求し、どう構図を取るか」を決めるのに対し、
こちらは**決まったものを実際の画像にする**ところを受け持つ。

## 立ち位置 ★重要

| | 扱い |
|---|---|
| `assets/_lib/` | **道具。** 毎回そのまま使う。書き換えない |
| `assets/tools/` | **道具。** モックの前処理・素材の合成・位置合わせ・確認用プレビュー |
| `assets/mockup/` | **素材。** 端末モックのフレームと画面の四隅 |
| `assets/samples/` | **サンプル。** 読んで考え方を持っていく。**コピーして使い回すものではない** |

**アプリごとに `content.js` と `style.css` は 1 から書く。** サンプルは「こう組める」を
示すだけで、そのアプリの目的に合わせて新規に書き起こす。だからサンプルには
「なぜその数字なのか」をコメントで残してある。数字ではなく**判断を持っていく**。

> **⚠ サンプルは Hioto（動画日記アプリ）の素材・配色・文言で書かれている。**
> 動かして確かめられるようにそうしてあるが、**そのぶん引きずられる**。実際、
> 別テーマで作らせた 3 体が揃って「同じ見出しに引っ張られる圧力が強い」と報告した。
> 対象が Hioto でもそうでなくても、**文言・配色・4 枚の構成は必ず自分で決め直す**。
>
> **とくに、作ろうとしている形式と同じ軸のサンプルがあるときは要注意。** 横 1 枚＋
> 2 台＋矢印を割り当てられた者が `explain-flow` を開き、縦つなぎ＋横倒しを割り当て
> られた者が `deep-tilt` を開くと、座標まで引きずられる。**表の説明だけ読んで、
> ファイルは開かない**方が速いことがある。

### 何を足せるかは決まっている

`_lib/compose.js` は道具なので書き換えない。つまり **`content.js` から置けるものが
表現の上限**で、これ以外の要素は追加できない。

`mock` / `mocks` / `breakout` / `arrow` / `badge` / `headline` / `sub` / `checklist` / `wordmark`

これ以外の飾り（章ラベル、罫線、帯など）が要るときは、**`variant` が `.v-<名前>` という
クラスになる**のを使い、`style.css` の擬似要素で足す。これが唯一の逃げ道なので、
設計の段階で「これだけで組む」と割り切っておく。

## 使いはじめ

作業場（`app-store-optimize-workspace` など）にコピーして始める。

```bash
SKILL=~/.claude/plugins/cache/tubasasakunn-marketplace/app-store-optimize/skills/screenshot-build

mkdir -p store-images/<slug> && cd store-images/<slug>
cp -r $SKILL/assets/_lib $SKILL/assets/tools $SKILL/assets/mockup .

mkdir -p portrait                                        # 縦セットなら portrait など
cp $SKILL/assets/samples/<近い型>/index.html portrait/    # 雛形として
```

置き場はこの形を前提にしている。

```
store-images/<slug>/
  _lib/  tools/  mockup/     ← スキルから展開したもの。git 管理外
  portrait/
    index.html               ← 読み込み順が決まっているだけ。そのまま使ってよい
    content.js  style.css    ← ★ここを 1 から書く
    out/                     ← 書き出した PNG
```

別の場所に `mockup/` を置くなら、`index.html` の先頭で `window.MOCKUP_DIR` を定義する。

`content.js` の画像パスは**このディレクトリからの相対**。作業場が
`<workspace>/store-images/<slug>/portrait/` なら、アプリの素材は `../../../apps/<slug>/material/...`。

`content.js` と `style.css` を新規に書く。

### ★ Playwright と実行する場所

`render.mjs` は `import { chromium } from 'playwright'` するので、**playwright が
入っているツリーの中から実行する**。`cd store-images/<slug>` した先には
`node_modules` が無いので、そこから叩くと `ERR_MODULE_NOT_FOUND` で落ちる。

```bash
# workspace のルートに置く。バージョンはキャッシュ済みのブラウザに合わせる
# （新しすぎると別ビルドを要求して再ダウンロードになる）
npm i -D playwright@1.59.1

# 実行はルートから。パスはルート起点で渡す
node store-images/<slug>/_lib/render.mjs store-images/<slug>/portrait
```

スキルの実体は marketplace のチェックアウト先にある。`~/.claude/plugins/cache/...`
に無ければ `~/workspace_tmp/claude-code-marketplace/...` を見る。

## 組み立て

### 1. サイズを決める

| キャンバス | ピクセル | 検索結果に出る枚数 |
|---|---|---|
| 縦 1 枚 | 1320×2868 | **3 枚** |
| 縦つなぎ | 2640×2868（2 枚）／ 3960×2868（3 枚）を分割 | 3 枚 |
| 横 1 枚 | 2868×1320 | **1 枚** |

**横を選んだ時点で検索結果は 1 枚**になり、そのアプリの全枚が横に固定される（縦横の混在は不可）。
つなぎは**最初から広いキャンバスで組んで切る**もので、あとから足せない。

他サイズは Apple 側が自動スケールするので、6.9" の 1 セットだけ作れば足りる。

### 2. content.js を書く

```js
window.CONTENT = {
  meta: { app: 'アプリ名', size: { w: 1320, h: 2868 } },
  theme: { /* CSS 変数になる。bgFrom → --bg-from */ },
  wordmark: { icon: '...', text: '...' },

  // 複数枚にまたがるもの。座標は「またぎキャンバス」（1320 × 枚数）
  spreads: [{
    pages: [0, 1],
    mock: { name: 'iphone-tilt', shot: '...png', w: 2500, x: 84, y: 836 },
    breakouts: [{ src: '...png', rect: [20, 830, 580, 200], w: 800, x: 120, y: 1900, rotate: -5 }],
  }],

  shots: [{
    variant: 'hero',                       // class 名になるだけ。任意の文字列でよい
    headline: ['1 行目', '<mark>2</mark> 行目'],   // 配列 = 改行位置を人が決める
    sub: '任意',
    checklist: ['☑ になる項目', '…'],
    wordmark: true,
    mock:  { name: 'iphone-flat', shot: '...png', w: 2550, x: -625, y: 650, rotate: -4 },
    mocks: [ /* 1 枚に複数台を置くとき */ ],
    breakouts: [ /* 切り出して飛ばす UI 片 */ ],
    arrows: [{ from: [560, 1980], to: [905, 1655], bend: 0.5, width: 17, head: 54 }],
    badge: { lines: ['1日', '3秒で'], x: '68%', y: '77%', rotate: -8 },
  }],
};
```

位置はすべて px（キャンバス座標）。`badge` だけ % で、中心を指す。

### 3. 端末モックに流し込む

`_lib/mockup.js` が、モックの**画面の四隅**へスクリーンショットを射影変換（ホモグラフィ）する。
Canva の Smart Mockup と同じ理屈で、違いは四隅を人が仕込むか自動検出するか。

フレーム画像は画面が抜いてある PNG で、スクリーンショットより**手前**に重ねる。
だから変形が数 px ずれても角丸やベゼルの内側で吸収される。

同梱のモック:

| name | 見た目 | **中身の傾き** | 画面/w | 本体幅/w | 向き |
|---|---|---|---|---|---|
| `iphone-flat` | 正面 | **0°** | 0.439 | 0.484 | 画面を読ませたい枚 |
| `iphone-tilt` | 縦のまま奥へ傾く | **23°** | 0.419 | 0.807 | 迫力を出したい枚 |
| `iphone-lay` | 横に寝かせる | **53°** | 0.387 | 0.968 | 映像・写真が主役の枚 |

要素の高さは `w` と同じ（モックは 1024 正方形）。

**「中身の傾き」は流し込んだ画面がどれだけ倒れるか。** 写真や映像が主役の枚では
ここが決め手になる。`iphone-lay` は 53° なので、**水平線のある写真は転んで見える**
——「傾いた端末の映像」ではなく「傾いた写真」になる。地平線・水平の 構造物 がある
素材なら `iphone-tilt`（23°）が上限と思ってよい。

**表示幅 `w` は画面から逆算する。** 「画面を 860px 幅で見せたい」なら

```
w = 860 / 0.439 = 1959     （iphone-flat の場合）
```

横 1 枚（高さ 1320）で端末を切らずに置きたいなら、`w` の上限は高さ側で決まる。

同じ値は `mockup/*.json` の `screen` / `body` / `size` にも入っている。
`body` は端末**本体**の外接矩形で、キャンバス中央に置く・下端を揃えるといった
配置はこちらを使う（`corners` は画面の四隅なので用途が違う）。

**モックを増やすとき**は、Canva 等で画面を単色で塗りつぶした PNG（背景は透過）を書き出して:

```bash
python3 tools/prep_mockup.py <モック.png> <名前> --debug
```

単色を抜いてフレーム PNG にし、画面の四隅を検出して JSON に書く。`index.js` も作り直す。
色は自動判定（緑である必要はない）、向きはノッチの位置で判定する。
**`--debug` で出る確認用 PNG を必ず一度は目で見る。**

### 4. 位置を合わせる

数値を先に決めなくてよい。画面上で動かす。

```bash
node tools/edit.mjs portrait
```

素材が作業ディレクトリの外にあるので、配信の基点は既定で 3 つ上まで開く。
届かなければ `--root <パス>` で指定する。

ドラッグで移動、ホイールで大きさ、矢印キーで 1px。重なって掴めない要素は右のパネルの
一覧から選ぶ。「保存」で `layout.js` に書き出され、`content.js` の値に被さる。

固まったら値を `content.js` へ写して `layout.js` を消す。**content.js を機械に書き戻させない**
——「なぜその数字か」のコメントが消えるため。

### 5. 書き出す

```bash
node _lib/render.mjs portrait
node _lib/render.mjs portrait --only 2,3   # 撮り直しは絞れる
```

`.shot` 要素を 1 つずつ撮るので、ビューポートに関係なく CSS 実寸がそのまま出力サイズになる。
読めなかった画像があるとそこで止まる。ページ内の JS エラーも拾って落とす。

出力は **RGB（アルファ無し）** なので、そのまま ASC に出せる（ASC はアルファ付き PNG を弾く）。

`?preview=1` を付けて開くと縮小して横並びになり、手元で素早く確認できる。

### 6. App Store の見え方で確認する ★必須

```bash
node tools/preview.mjs portrait/out --label "案の名前" \
  --app Hioto --sub "撮るだけでのこる、動画の日記" \
  --icon ../../apps/hioto/material/app_icon_1024.png \
  -o preview.html
```

**人に見せるときは必ずこの形にする。** 4 枚を平らに並べただけでは、

- 縮小表示で読めなくなる見出し
- 詳細ページで崩れるまたぎ
- 検索結果に 4 枚目が出ないこと

に気づけない。出力は画像を data URI で埋め込んだ 1 枚の HTML なので、そのまま
Artifact として公開できる。複数の `out` を並べて渡すと案を横に比較できる。

## 設計の軸

型を選ぶのではなく、目的から軸を組み合わせる。上の軸ほど後戻りしにくい。

1. **キャンバス** — 縦 1 枚 / 縦つなぎ / 横 1 枚 ★ここだけは後から変えられない
2. **端末の見せ方** — 種類・回転・大きさとはみ出し・台数。**ここで文字に使える面積が決まる**
3. **素材と装飾** — そのまま / 切り出して飛ばす / 矢印でつなぐ
4. **文字の役割** — 見出し（必須）/ サブ / ☑ の箇条書き / 円形バッジ / ワードマーク
5. **タイポ** — 大きさ・太さ・色・蛍光ペン・差し色
6. **背景** — 単色 / グラデーション / 円弧などの図形

### 軸は独立していない

| 選ぶもの | 得るもの | 失うもの |
|---|---|---|
| 横 1 枚 | 1 枚の情報量。手順の説明ができる | 検索結果が 3 枚 → 1 枚。全枚が横に固定 |
| 縦つなぎ | 検索結果 3 枚並びでの一体感 | 詳細ページでは余白が入って崩れる |
| 端末を目一杯 | 画面そのものの訴求力 | 文字の置き場と、**切り出せる大きさ**（後述） |
| パース付きモック | 奥行きと迫力 | 画面の文字が潰れる |
| ☑ の箇条書き | 機能を数で示せる | 縮小表示では読めない。詳細ページ専用の情報になる |

### 端末を目一杯にすると、切り出しも大きくできない

iPhone の画面比 2.19 とキャンバス比 2.17 はほぼ同じ。つまり**画面をキャンバス幅
いっぱいにすると、縦もちょうど収まってしまう**。はみ出させるには幅を超えさせる
しかなく、その瞬間に画面幅 ≒ キャンバス幅になる。

すると**全幅のカード（設定画面の行など）は 1.1 倍を超えると中の文が画面外へ出る**。
端末を大きく使う型では、切り出す対象は「全幅のカード」ではなく
**その中の一点**（トグル、ボタン、チップ）を選ぶことになる。

### 見出しの大きさは幅から逆算する

「縮小で読めない見出しにするな」だけでは決まらない。**入る文字数から先に決める**。

```
font-size ≦ 使える幅 ÷ (文字数 × 0.89)
```

`0.89` は和文 1 文字の実効幅（weight 800・`letter-spacing: -.045em`・`palt` 有効での実測）。
1320 幅・左右パディング 96 なら使える幅は 1128 なので、8 文字の行は 158px まで置ける。

読める下限の目安は、**検索結果でのサムネイル幅**から決まる。

| | サムネイル幅 | 1320 幅での見出し下限 |
|---|---|---|
| 縦（3 枚並ぶ） | 約 114px | 100px 前後 |
| 横（1 枚だけ） | 約 380px | もっと小さくても読める |

### 選ぶ順序

1. **検索結果に並ぶ 3 枚で何を言うか決める** — ここがすべての上流
2. **キャンバスを決める** — 後戻りできない
3. **端末の見せ方を決める** — ここで余る面積が決まる
4. **余った面積に何を置くか**
5. **タイポと背景を決める** — ここは後からいくらでも振り直せる

### ★ 複数の案を作るなら、軸 1・2 を先に振り分ける

**訴求テーマだけ変えて軸を任せると、案が全部同じレイアウトになる。**

別テーマ（手軽さ / 情緒 / プライバシー）で 3 案を作らせたところ、3 体とも
「縦 1 枚 ×4・`iphone-flat`・端末は中央・見出しは上」に収束した。色と文言は
違うのに、並べると同じ絵に見える。**迷ったときに安全な選択へ寄るのは当然**なので、
テーマだけでは散らない。

案を比べたいなら、**キャンバス（軸 1）と端末の見せ方（軸 2）を先に割り当てる**。

| | キャンバス | 端末 |
|---|---|---|
| 案 1 | 縦 1 枚 | 正面・収める |
| 案 2 | 縦つなぎ | パースまたは回転・全方向へはみ出す |
| 案 3 | 横 1 枚 | 2 台＋矢印 |

そのうえでテーマを載せる。軸 3〜6 は任せてよい。

## 素材の解像度

**スクリーンショットは 1320 幅で使うぶんの解像度が要る。** 端末モックの画面に引き伸ばすので、
LP 用に縮小した画像（620px 幅など）を使うと UI の細線が甘くなる。
シミュレータから撮った原寸（1206×2622 など）を使う。

### 原寸が単色で塗られていたら

動画・カメラを扱うアプリは、シミュレータで実際の映像を撮れない。そのため
**原寸のスクリーンショットは映像領域が単色（swift-base 系は純緑 `#00FF00`）で
塗られている**ことがある。ここで「完成版が低解像度しか無い」と諦めない。

```bash
python3 tools/fill_chroma.py <原寸スクショ.png> <差し込む画像.jpg> -o screens/<名前>.png
```

置き換えではなく**アンコンポジット**するので、単色の上に乗っている半透明の UI
（シャッターリング・タブバー・照準）が潰れない。素材は `material/footage/` のような
場所に用意されていることが多い。

**低解像度の完成版しか無いように見えても、まず「原寸＋素材から作り直せないか」を
確認する。** 別々に走らせた 3 体が全員この道を選んだ。
