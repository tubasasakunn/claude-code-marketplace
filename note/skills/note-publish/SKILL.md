# note の下書きを公開する

**これは本人アカウントでの実公開。取り消しても「公開された事実」は消えない。**

必ず **1 本ずつ**、**ユーザの明示的な承認を取ってから**公開する。
「全部公開して」と言われても 1 本ずつ確認する。

## 1. 対象を特定する

```
note_list_articles(status="draft")
```

どれを出すか曖昧なら、**推測せずユーザに聞く**。タイトルと記事キーを並べて確認する。

## 2. 実物を見る

```
note_show_preview(article_key="n...")
```

**プレビューを必ず開く。** ローカルの Markdown が正しくても note 側の変換で崩れる。

## 3. 公開前チェック

| 見るところ | 落ちていたら |
|---|---|
| アイキャッチが設定されているか | `note_upload_eyecatch` で入れる。ないまま出さない |
| 画像がすべて note の URL になっているか | ローカルパスが残っていたらアップロード失敗。作り直す |
| タイトル | `note-craft` の基準（具体・煽らない・30〜40字） |
| タグ 3〜5 個 | 多すぎ・関連の薄いタグを削る |
| 見出しの階層・リストの入れ子 | 崩れていたら Markdown を直して `note_update_article` |
| **事実・数字・固有名詞** | 出典のない数字、記憶で書いた仕様、実在の個人・企業への言及を潰す |
| **未公開情報** | 未リリースのアプリ名、審査中の情報、秘密鍵・トークン・内部 URL が混ざっていないか |
| 有料記事なら | 無料部分だけで 1 本として成立しているか。有料ラインの位置と価格 |

**1 つでも引っかかったら公開しない。** 直して下書きを更新し、もう一度プレビューから。

## 4. ユーザに確認を取る

タイトル・タグ・冒頭 3 行・アイキャッチの有無・公開 URL の予定を提示して、
`AskUserQuestion` で明示的に承認を取る。**承認なしに次へ進まない。**

## 5. 公開する

```
note_publish_article(article_id="<記事ID>")
```

新規作成と同時公開（`title` / `body` を渡す形）も API 上はできるが、**使わない**。
下書き → プレビュー確認 → 公開の順を必ず通す。

## 6. 記録する

- `articles/README.md` の状態を `下書き` → `公開 2026-08-02` に更新し、公開 URL を書く
- ローカルの `article.md` と note 側に差があれば、ローカルを正本として揃えておく

## 公開後

- **すぐ実物の公開ページを開いて確認する。** プレビューと公開後で表示が違うことがある
- 直すなら `note_update_article`。公開済み記事も更新できる
- 取り下げたいときは note の Web UI から。`note_delete_draft` は**公開済みには効かない**

## やらないこと

- **一括公開しない。** `note_list_articles` の結果をループで publish に流すような操作はしない
- **予約公開・定時実行に組み込まない。** 人が見ていない時間に公開が走る形にしない
- **`note_delete_all_drafts` を使わない**（`/note:note-setup` と同じ理由）
