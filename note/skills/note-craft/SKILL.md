# note-craft — 良い note 記事を書く

**記事を書くときは毎回これを読む。** 手順は `/note:note-post`、公開は `/note:note-publish`。

## 正本（必読）

- **[[NOTES]]** … ★**毎回読む**。ユーザが確定した指摘・好みの蓄積。
  **一般原則と矛盾したらこちらが優先**
- 文章そのものの規範は **`writing` プラグイン**が正本。本文を書く前に読む
  - `japanese-tech-writing` … 一文一行、パラグラフライティング、論証の穴、LLM っぽい空句の禁止
  - `cognitive-rhythm-writing` … 緩急＝認知モードの切替。「密度はあるが平坦」の診断と修正

**この 2 つを読まずに本文を書かない。** note-craft が決めるのは「note という媒体でどう出すか」だけで、
日本語の質は writing 側が持つ。

## note はどういう媒体か

- **検索より回遊とタイムライン。** SEO 記事のつもりで書くと、note の中では読まれない
- **書き手の顔がある。** 一人称・実体験・失敗が資産になる。無記名で書ける内容は note でなくていい
- **スキ／フォローは記事単位ではなく人単位で積む。** 1 本のバズより、同じ人が次も読む状態を作る
- **読者はスマホで縦に流す。** 長い段落と、見出しのない長文が最も落とされる

## タイトル

**タイトルで 9 割決まる。本文より時間をかける。**

- **具体 > 抽象。** 数字・固有名詞・期間・結果を入れる
  - ✗「個人開発でアプリを作った話」
  - ○「個人開発の iOS アプリを 22 本出して、伸びたのは 3 本だった」
- **検索流入を狙う記事では、宣伝対象の名前をタイトルに出さない。**
  入れるのは読者が検索しそうな語と、その課題への結論。名前は本文の中盤で初めて出す
  - ✗「話す日記帳という音声日記アプリを作りました」
  - ○「日記が続かないのは意志の問題ではない。原因は『書く』という工程にある」
  - 名前を知らない人は名前で検索しない。名前をタイトルに置くと既知の人にしか当たらない
- **煽らない。** 「衝撃の」「まさかの」「知らないと損」は note では安っぽく見える
- **問いか、結論か、数字**のどれかで始める。両論併記のタイトルは弱い
- 30〜40 字。スマホで 2 行に収まる範囲

## 書き出し（最初の 3 行）

**ここで離脱の大半が決まる。**

- **前置きを書かない。** 「こんにちは、〇〇です」「今回は〜について書きます」は削る
- **いきなり具体から入る。** 数字、場面、失敗、意外な事実
- **記事の結論を最初に置いてよい。** note の読者は「結論を先に見て、理由を読むかどうか決める」

## 構成

```
書き出し（具体・結論）
 → 前提（読者が何を知っていれば読めるか。最小限に）
 → 本体（見出し 3〜6 個。1 見出し = 1 主張）
 → 転（うまくいかなかったこと・例外・限界）
 → 締め（読者が次にできること）
```

- **見出しは H2 を主に使う。** H3 は本当に階層が要るときだけ。H1 はタイトルが持つので本文で使わない
- **1 段落 3〜4 行まで。** スマホで塊に見えたら分ける
- **「転」を必ず入れる。** うまくいった話だけの記事は信用されないし、読み返されない
- 箇条書きは**要素が並列のときだけ**。論証を箇条書きに逃がすと薄くなる

## 図・画像

### アイキャッチ

- **必須。** ないとタイムラインで存在感が消える
- **note 用に作る。ストア画像や SNS 画像の切り出しで済ませない。**
  タイムラインに出るのは**幅 300px 前後**。大画面前提の副文は表示上 7px 相当になって読めない
- **文字は主題 1 フレーズだけ。** 1280px 幅の原寸で**主題 90px 以上**（300px 表示で 21px 相当）。
  タイトルの全文を画像に焼かない
- **作ったら実寸で目視する。** 300px と 208px に縮小して Read で開き、主題が読めるか見る。
  読めなければ作り直す
- 実装は `/canva:canva-image-gen`（AI 生成）、`sns-marketing` の `carousel-craft` の
  ブランド描画（アプリ宣伝記事なら SNS カルーセルと**同じ見た目に揃える**）、
  または Pillow で組む（ブランド色を厳密に合わせたいとき）

### 本文中の画像

- **主張の証拠になるものだけ。** 飾りのフリー素材は入れない
- **記事の背骨は図にする。実画面のスクショだけで済ませない。**
  スクショが示せるのは「そういう画面がある」ことまで。
  主張の構造（何がどう減るのか、何と何が違うのか、順序はどうなっているか）は図でしか伝わらない。
  比較表・工程図・Before/After の対比を 1 枚作り、アプリのブランド色とスクショに揃える
- 図の文字は、note の本文幅（約 620px）に縮んでも読めるサイズにする。
  原寸 1200px なら**本文 34px 以上**（表示 18px 相当）
- そのほかに証拠になるもの: アプリの実画面、グラフ、実際のログ
- 画像は `articles/<slug>/images/` に置き、Markdown から相対パスで参照する
  （`note_create_from_file` が自動でアップロードして URL に置換する）

## タグ

- **3〜5 個。** 10 個並べても効かない。関連の薄いタグは信頼を落とす
- **大（#プログラミング）・中（#個人開発）・小（#SwiftUI）を混ぜる**
- note の公式お題・コンテストに合致するときは、そのタグを必ず入れる（露出が別枠で増える）
- 迷ったら note 内で同ジャンルの記事を検索し、実際に使われているタグを見る

## 有料記事にするなら

- **無料部分だけで 1 本として成立させる。** 「続きは有料」で切るために内容を薄くしない
- 有料ラインの位置は「無料部分を読んで満足した人が、さらに手を動かしたくなる」ところ
- 値付けは 100〜500 円が入口。**初回から高くしない**
- 有料にする価値があるのは、**手順・設定値・実データ・失敗の詳細**。考察は無料でいい

## やらないこと

- **AI が書いたとわかる文体で出さない。** 「〜と言えるでしょう」「いかがでしたか」
  「重要なポイントは3つあります」は `japanese-tech-writing` が禁じている。必ず点検する
- **他媒体のコピペをそのまま置かない。** Zenn / X / ブログと同じ本文を出すなら、
  書き出しと構成は note 向けに作り直す
- **公開を自動化しない。** 下書きまでが機械の仕事（理由は `/note:note-setup`）
