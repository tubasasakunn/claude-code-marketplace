# LINE 越しにユーザとやり取りする (talk_to_user)

## いつ使うか

ユーザがターミナルの前にいない前提で、長時間の作業（アプリ1本を審査提出まで、など）を進めるとき。

- **報告する**: 節目ごとに何が終わったかを伝える
- **問う**: 自分では決められないこと（プロダクト判断、破壊的操作の許可）を聞いて待つ
- **依頼する**: 2FA など、原理的に自動化できない操作をお願いする

## 大原則

**ユーザの時間を奪わない。** 通知は少なく、1通に必要なことを全部入れる。

- 進捗の実況をしない。**節目だけ**（スキル1本の完了、事故、判断待ち）
- 「〜しましょうか？」と聞かない。**自分で決められることは決める**
- 聞くときは**選択肢を示す**。「A か B か、理由はこう」。自由記述を強いない
- 悪い知らせを先に、短く。**何が壊れ、何が無事で、どうするか**の順

## 道具

`${CLAUDE_PLUGIN_ROOT}/scripts/line_ask.sh`。harness の LINE API を叩く。既読管理は要らない
（送信直前の最新 timestamp を控え、それより新しい返信を待つ）。

```bash
export LINE_ASK=${CLAUDE_PLUGIN_ROOT}/scripts/line_ask.sh
```

## 報告だけする（返信を待たない）

```bash
export HARNESS_TOKEN=$(grep '^API_TOKEN=' ~/workspace/harness/.env | cut -d= -f2-)

curl -s -X POST https://harness.basaapp.com/api/line/push \
  -H "Authorization: Bearer $HARNESS_TOKEN" -H "Content-Type: application/json" \
  -d "$(python3 -c '
import json
text = """✅ Bide の審査提出が完了しました

appStoreState: WAITING_FOR_REVIEW
結果が出たら Apple のメールを拾って報告します。"""
print(json.dumps({"messages": [{"type": "text", "text": text}]}, ensure_ascii=False))
')" > /dev/null
```

`to` を省略すると `LINE_USER_ID` 宛（＝ユーザ）に飛ぶ。

**メッセージは Python の `json.dumps` で組み立てる。** シェルの `-d '{...}'` に日本語や改行を直に埋めると壊れる。

## 問うて、返信を待つ ★これが本題

```bash
# 前面で待たない。バックグラウンドで走らせて、完了通知で起きる。
"$LINE_ASK" --timeout 3600 "アプリ名 Bide は App Store で既に使われていました。

A) Bide：待ち方の記録  （CONCEPT.md のストア表示名。これで進めます）
B) 別の名前を考える

A で進めてよければ「A」と返信してください。" &
```

**必ずバックグラウンドで実行する**（`run_in_background: true`）。返信が来た時点でスクリプトが終了し、
その完了通知で起きられる。フォアグラウンドで待つとセッションが固まる。

- 返信が来た → 本文が stdout に出て終了コード 0
- 時間切れ → 終了コード 1

### 返信を待つあいだ、手は止めない

返信待ちの間に、**返信に依存しない作業を進める**。1時間ぼんやり待つのは無駄。

依存する作業しか残っていないなら、`--timeout` を長めにして待つ。

### 送信済みの問いに対する返信だけ待つ

```bash
"$LINE_ASK" --wait-only --timeout 1800
```

## 見せて決める（デザインなど）

文章では伝わらないもの——**配色、画面のムード、AppIcon、ストア画像**——は
アーティファクトにして URL を LINE で送る。

1. HTML を書いて `Artifact` ツールで公開する（claude.ai にホストされ、URL ができる）
2. その URL を LINE で送り、選択肢を添えて返信を待つ
3. 返信を受けて HTML を直し、**同じファイルパスで再公開する**（URL は変わらない）

```bash
"$LINE_ASK" --timeout 3600 "❓ Bide の配色を3案作りました。

https://claude.ai/public/artifacts/xxxx

A) 琥珀（灯りの温かさ）
B) 藍（夜の静けさ）
C) 灰（無色の待ち時間）

番号か記号で返信してください。理由があれば添えてください。" &
```

- **1画面に全案を並べる。** 別々のアーティファクトにすると比較できない
- **選択肢に名前を付ける。** 「A/B/C」だけでなく「琥珀」のように呼べる語を与える
- アーティファクトは外部 CDN を使えない。**CSS も画像も全部インラインにする**
- スマホで見る。**縦に並べ、横スクロールさせない**

再公開は同じファイルパスで `Artifact` を呼び直す。URL が変わるとユーザが古い方を見る。

## 何を聞き、何を聞かないか

**聞く**（ユーザにしか決められない）:

- プロダクト判断（アプリ名、コンセプトの方向転換、公開するか否か）
- 破壊的操作の許可（審査提出の取り下げ、リポジトリの削除、公開済みレビューへの返信）
- 2FA が要る操作の依頼（Xcode の Apple ID サインイン、ASC のログイン）
- 費用が発生する操作

**聞かない**（自分で決める）:

- 実装の細部、ファイル構成、命名
- リトライするかどうか
- どのスキルを次に走らせるか
- エラーの直し方

## 迷ったとき・困ったとき

**「聞くべきか」で迷ったら、この順に自問する。**

1. **戻せるか。** 戻せるなら、まず自分でやってから報告する。聞かない
2. **自分で調べて分かるか。** ログ・API・ソースを読めば決まるなら、読む。聞かない
3. **ユーザの好みで答えが変わるか。** 変わるなら聞く（デザイン、アプリ名、公開の可否）
4. **失敗したら誰かに迷惑がかかるか。** かかるなら聞く（公開レビューへの返信、審査提出の取り下げ）

### 詰まったときの報告の型

**黙って止まらない。何分も同じエラーを叩き続けない。** 2〜3回試して駄目なら、いったん報告する。

```
❓ Xcode Cloud のビルドが3回連続で落ちています

エラー: ci_post_clone.sh script failed (exited with code 1)
調べたこと: .xcodeproj が git 管理外で、clone 直後に存在しないため
やろうとしていること: ci_post_clone.sh に xcodegen 生成を挟む

このまま進めてよければ「go」と返信してください。
15分待って返信がなければ、自分の判断で進めます。
```

**「返信がなければこうする」を書く。** ユーザが寝ているかもしれない。
止まったまま朝を迎えるより、戻せる範囲で前に進む方がよい。

### 手詰まりのとき

自動化できないものに当たったら、**代替案を2つ持って**聞く。「できません」だけを送らない。

```
🔑 アプリのプライバシー宣言に ASC のログインが要ります

公式 API には存在せず、Cookie 認証しか受け付けません（調査済み）。

A) リレーの URL をスマホで開いてログイン（1分。以後30日有効）
   https://harness.basaapp.com/relay/xxxx
B) 今回は私が ASC の画面を操作するので、Mac の前に来られるときに教えてください

A をおすすめします。
```

## 依頼するときは、手順を書く

ユーザは背景を知らない。**リンクと、押すボタンまで書く。**

```
🔑 Xcode の Apple ID サインインをお願いします

Xcode → Settings → Accounts

切れると Integrate > Create Workflow… が無効になり、
Xcode Cloud の設定ができません。2FA が要るので私では代行できません。

済んだら「done」と返信してください。続きを進めます。
```

## 事故を報告するとき

**隠さない。順番を守る。** 何が壊れたか → 何が無事か → どうするか。

```
⚠️ 事故が1件あります

Bide の CI 設定中に、Xcode が Nagasu の ciProduct を流用して Bide に付け替えました。
結果、Nagasu の Xcode Cloud CI が消えています。

無事なもの: Nagasu のアプリ本体・アップロード済みビルド・審査提出（WAITING_FOR_REVIEW）
失われたもの: CI 設定のみ。作り直せます

対処: 再発防止のスナップショット比較をスキルに組み込みました。
Xcode の再サインインが済んだら CI を作り直します。
```

## 絵文字は1通に1つまで

種類で意味を持たせる。乱発すると読み飛ばされる。

| 記号 | 用途 |
|---|---|
| ✅ | 完了 |
| ⚠️ | 事故・要注意 |
| 🔑 | ユーザ操作の依頼 |
| ❓ | 判断待ち |
| 📮 | 設定の不備 |

## 罠

### 返信が検知できない

`line_ask.sh` は**送信直前の最新 timestamp より新しいメッセージ**を待つ。
スクリプトを起動する前にユーザが返信していると、それは拾えない。
その場合は `GET /api/line/users/<id>/messages?limit=5` を直接見る。

### 複数の問いを同時に投げない

どの問いへの返信か区別できない。**1問ずつ、返信を得てから次へ。**

### 長文を送らない

LINE は1通あたりの表示が限られる。**要点3つまで。** 詳細はアーティファクトや URL に逃がす。

## 実証済みであること

このスキルの往復は実地で確認してある（2026-07-10）。
`line_ask.sh` で問いを送り、ユーザの返信「ok」をポーリングが検知し、
バックグラウンドコマンドの完了通知でエージェントが起きるところまで通した。

## 完了条件

- [ ] 節目ごとに報告した（実況していない）
- [ ] 問いには選択肢を添えた
- [ ] 待機はバックグラウンドで行い、その間も手を動かした
- [ ] 事故は隠さず、無事なものと対処を添えて報告した
