# AI 時代のコーディング規約

このリポジトリの主たる保守者は AI エージェント（Claude Code）である前提の規約。
エージェントはセッションごとに記憶を失う——**その行を編集するとき確実にコンテキストに
入っている記憶は、その行の隣にあるコメントだけ**。会話ログや PR 説明は次のセッション
では読まれない前提で、文脈をコードに残す。

コメントは「少なく・短く・why だけ・現場に」。量産すると本当に重要な注意書きが
埋もれる（`swift-conventions.md` の「コメントは why だけ」と同じ原則の拡張）。

## バグ修正には「バグ台帳コメント」を必ず残す

バグを直したら、修正箇所の直近に **症状・発火条件・この形の修正が正しい理由** を書く。
これが無いと、未来のエージェントが「不自然に見えるコード」をリファクタして
同じバグを再導入する（回帰の最大要因）。

```swift
// AIDEV-NOTE: バグ修正(2026-07) 録画停止直後の export が 0 秒動画になることがあった。
// 原因: duration の非同期ロード完了前に読んでいた。必ず load(.duration) を待つこと。
let duration = try await asset.load(.duration)
```

- あわせて**そのバグを再現する回帰テスト**を残す（バグ名がわかるテスト名で）。
  「発火条件の外では挙動が変わらない」ことも重要な仕様——安易な守り
  （guard 節・try? の追加）で直すと別の回帰を生む。
- コメントは PR 説明の代わりではなく**コード側に**書く。エージェントが次に読むのは
  コードであって PR 履歴ではない。
- **現在形の制約として書く**。「以前は〜だった」「今回〜に変更した」という diff の
  説明は書かない（マージした瞬間に意味を失う）。何をしたかは commit message へ、
  なぜ今こうなのかはコメントへ。

## 直感に反するコードには「ガードコメント」

一見「統一できそう」「消せそう」「簡略化できそう」だが、してはいけないコードには、
**その場で**理由と「やってはいけない変更」を明示する。禁止だけ書いても
（人間と同様に）エージェントは上書きする——**理由まで書いた禁止だけが守られる**。

```swift
// AIDEV-NOTE: ここは Task ではなく DispatchQueue のまま。50ms 周期のリズム保証が
// 必要で、構造化並行性にはスケジューリング保証が無い（docs/adr/0003 参照）。
```

対象の典型：
- 順序依存（この行を先に呼ばないとクラッシュ／デッドロック）
- わざと重複させているコード（DRY にすると別々に変更できなくなる）
- 一見不要な待ち・リトライ・キャッシュ無効化（実機でしか再現しない問題への対処）
- SDK のバグ・未文書化挙動への回避策（workaround である旨 + 参照 URL）
- 計測の結果あえてそう書いた性能コード（計測値を添える）

## アンカーコメントの運用

- 上記のような「エージェント向けの重要な注意書き」には **`AIDEV-NOTE:`** プレフィックス
  を付ける（grep で全列挙できる）。未解決の懸念は `AIDEV-TODO:`。
- 該当箇所を編集する前に、**周辺の `AIDEV-` を検索して読む**。
- **`AIDEV-NOTE` は人間の明示的な指示なしに削除・改変しない**。前提が変わる変更を
  したときは、同じ diff でコメントも更新する（嘘になったコメントは事故の種）。
- 横断的な設計判断は ADR に書き、コード側からは `// docs/adr/NNNN 参照` で結ぶ。
  コメントと ADR は排他ではなく連結。スニペットのコピーではなく参照
  （`ファイル:行` / ADR 番号）で指す——コピーはすぐ古くなる。
- **参照は「永続するもの」だけを引く**。ADR 番号・仕様書のセクション・OS/SDK
  バージョン・再現手順は可。セッションの会話・「ユーザーに言われたので」・チャット
  履歴は不可（次のセッションからは辿れない）。理由そのものをコメントに書き下す。

## 強制力のランキング：機械 > テスト > コメント > 散文

不変条件を残す場所は強い順に選ぶ：

1. **型・コンパイラ**：網羅 switch・non-optional・enum で不正状態を表現不能にする
   （破ったらビルドが割れる。最強のガードレール）。
2. **テスト**：仕様は実行可能な形で。「このチェックを通れば OK」という 1 コマンドが
   あればエージェントは自走できる。
3. **lint / hook / スクリプト**：機械的に検査できる規約を散文で書かない
   （`/swift-app:audit-conventions` の grep パターンに落とす）。
4. **コード現地のコメント**：機械化できない文脈（why・経緯・禁止の理由）だけ。
5. **CLAUDE.md / rules の散文**：最後の手段。全 Swift ファイルに効く一般則のみ。

Debug 限定の前提は `assert`、出荷後も守るべき契約は `precondition`。
「〜のはず」をコメントだけで済ませない。

## エージェントが読める・探せるコードにする

- **grep できる名前を付ける**。識別子・キー・通知名を文字列連結や補間で組み立てない
  （`"user_" + id` で作ったキーは検索で見つからない）。
- **同じ概念には層を跨いで同じ名前**を使う（API では snake_case・Swift では camelCase の
  ような機械変換は仕方ないが、意味的な別名を発明しない）。
- **挙動はその場に**（locality of behavior）。1 画面の挙動を追うのに 5 ファイル
  跳ばせる間接層を作らない（`swift-architecture.md` の「protocol を先回りで切らない」と同根）。
- リフレクション・文字列ベースのディスパッチなど**静的に追えない仕組みを使わない**。
  コンパイラが追えないものはエージェントも追えない。
- 分割は「自己完結した小ささ」を狙う。ファイルを細切れにしすぎると読む回数が増えて
  逆にコンテキストを浪費する（500 行分割ルールとのバランス）。

## 変更のたびに「次のセッションへの引き継ぎ」を更新する

- 罠を踏んだら CLAUDE.md セクション 6（既知ハマりどころ）へ、判断をしたら `/swift-app:adr` へ、
  規約になる知見なら `.claude/rules/` へ——**同じ作業の中で**書き足す。
  「あとでまとめて」は書かれない。
- ルールは失敗駆動で足す：エージェントが同じ間違いを 2 回したら、その失敗を防ぐ
  1 行を rules か hook に追加する。先回りの一般論でルールを太らせない。
- 検証コマンド（ビルド・テスト・スクリプト）はコピペで動く形で CLAUDE.md に残す。
- 作業を中断するときは、途中状態と次の一手をコミットメッセージに残す
  （未 push の暗黙状態を作らない）。
