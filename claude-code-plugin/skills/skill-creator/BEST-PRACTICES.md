## コア原則

### 1. 簡潔さが鍵

コンテキストウィンドウは共有リソースです。スキル内のすべてのトークンが会話履歴と競合します。

**デフォルトの仮定**: Claudeは既に非常に賢い

**各情報に問いかける**:
- Claudeは本当にこの説明が必要か？
- Claudeがこれを知っていると仮定できるか？
- このパラグラフはトークンコストに見合う価値があるか？

**良い例（約50トークン）**:
````markdown
## PDFテキスト抽出

pdfplumberでテキスト抽出:

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

**悪い例（約150トークン）**:
```markdown
## PDFテキスト抽出

PDF（ポータブルドキュメントフォーマット）ファイルは、テキスト、画像、
その他のコンテンツを含む一般的なファイル形式です。PDFからテキストを
抽出するには、ライブラリを使用する必要があります。PDF処理に利用可能な
ライブラリは多くありますが、使いやすく、ほとんどのケースに対応している
ため、pdfplumberをお勧めします...
```

### 2. 適切な自由度を設定

タスクの脆弱性と可変性に特異性レベルを合わせます。

**高い自由度**（テキストベースの指示）:
- 複数のアプローチが有効
- 決定はコンテキストに依存
- 例: コードレビュー、ドキュメント作成

```markdown
## コードレビュープロセス

1. コード構造と組織を分析
2. 潜在的なバグやエッジケースをチェック
3. 可読性と保守性の改善を提案
4. プロジェクト規約への準拠を確認
```

**低い自由度**（具体的なスクリプト）:
- 操作は脆弱でエラーが発生しやすい
- 一貫性が重要
- 例: データベースマイグレーション、デプロイ

````markdown
## データベースマイグレーション

このスクリプトを正確に実行:

```bash
python scripts/migrate.py --verify --backup
```

コマンドを変更したり、フラグを追加しないでください。
````

### 3. 使用予定のモデルでテスト

スキル効果は基礎モデルに依存します。

| モデル | 考慮事項 |
|:-------|:---------|
| Haiku | スキルは十分なガイダンスを提供しているか？ |
| Sonnet | スキルは明確で効率的か？ |
| Opus | スキルは過度な説明を避けているか？ |

Opusで完璧に機能するものは、Haikuではより詳細が必要な場合があります。

## スキル構造

### 命名規則

**動名詞形を推奨**（動詞 + -ing）:
- `processing-pdfs`
- `analyzing-spreadsheets`
- `managing-databases`
- `testing-code`

**許容される代替案**:
- 名詞句: `pdf-processing`
- アクション指向: `process-pdfs`

**避けるべき**:
- 曖昧: `helper`、`utils`
- 過度に一般的: `documents`、`data`
- 予約語: `anthropic-helper`、`claude-tools`

### 効果的な説明

**三人称で書く**（システムプロンプトに挿入されるため）:
- ○ 「Excelファイルを処理してレポートを生成します」
- × 「Excelファイルの処理をお手伝いできます」

**具体的で主要な用語を含める**:
```yaml
description: PDFファイルからテキストと表を抽出し、フォームに入力します。PDF、フォーム、ドキュメント抽出について言及された場合に使用してください。
```

**厳密な要件の場合**:

### 例パターン

入出力ペアを提供:
````markdown
## コミットメッセージ形式

**例1:**

出力:
```
feat(auth): JWTベースの認証を実装

````

### ワークフローパターン

複雑なタスクをステップに分解:

````markdown
## ワークフロー

進捗チェックリスト:
```
- [ ] ステップ1: フォーム分析
- [ ] ステップ2: フィールドマッピング作成
- [ ] ステップ3: マッピング検証
- [ ] ステップ4: フォーム入力
- [ ] ステップ5: 出力確認
```

**ステップ1: フォーム分析**
```bash
python scripts/analyze_form.py input.pdf
```

**ステップ2: フィールドマッピング作成**
`fields.json`を編集して値を設定。

**ステップ3: マッピング検証**
```bash
python scripts/validate_fields.py fields.json
```

**検証が成功したときのみ続行**
````

### フィードバックループ

バリデータ実行 → エラー修正 → 繰り返し

```markdown
## ドキュメント編集プロセス

1. `word/document.xml`に編集
2. **すぐに検証**: `python scripts/validate.py unpacked_dir/`
3. 検証失敗時:
   - エラーメッセージを確認
   - XMLを修正
   - 検証を再実行
4. **検証成功時のみ続行**
5. リビルド: `python scripts/pack.py unpacked_dir/ output.docx`
```

## 評価と反復

### 評価駆動開発

1. **ギャップを特定**: スキルなしでタスク実行、失敗を文書化
2. **評価を作成**: ギャップをテストする3つのシナリオ
3. **ベースラインを確立**: スキルなしのパフォーマンスを測定
4. **最小限の指示を作成**: ギャップに対処するのに必要なコンテンツのみ
5. **反復**: 評価実行、比較、改善

### Claudeを使用した反復開発

**新規スキル作成**:

1. スキルなしでタスクを完了
2. 再利用可能なパターンを特定
3. Claudeにスキル作成を依頼
4. 簡潔性をレビュー
5. 情報アーキテクチャを改善
6. 同様のタスクでテスト
7. 観察に基づいて反復

**監視すべきパターン**:

- 予期しない探索パス
- 接続の欠落
- 特定セクションへの過度な依存
- 無視されたコンテンツ
