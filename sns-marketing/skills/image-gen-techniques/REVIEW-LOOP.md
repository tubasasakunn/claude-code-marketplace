# REVIEW-LOOP.md — Claude Code のビジュアルフィードバックループ

Claude Code は Read ツールで画像ファイルを vision 入力として「見る」ことができる。
このループ（生成 → Read で目視 → 修正）を速く・確実に回すための規範。

---

## 1. Claude のビジョンの限界（公式仕様）を前提にする

| 限界 | 内容 | 対策 |
|------|------|------|
| 解像度上限 | 画像は長辺 ~1568px（高解像度ティアでも ~2576px）を超えると自動縮小される | 送る前に自分でリサイズ/クロップして制御する |
| 小さい文字 | 縮小後 ~12px 未満相当のフォントは誤読・見落としが起きる | 細部は**拡大クロップを別途 Read** |
| 空間推論 | 座標・位置の出力は「近似的」と公式に明言 | px 単位の判定は目視に頼らず機械計算 |
| カウント | オブジェクト個数は概算 | 枚数・要素数チェックはコードで |
| 低品質画像 | 200px未満・強いJPEG圧縮・回転はハルシネーション要因 | レビュー用画像は PNG / 高品質で |

**実務ルール**: 1080×1920 のフル画像やコンタクトシートは俯瞰用。フック文言・CTA・小さな
ラベルの判読は、該当領域だけ切り出した等倍〜拡大クロップを追加で Read する。
複数画像を渡すときは各画像の前に短いラベルを付ける（「Image 1: 全体」「Image 2: CTA拡大」）。

---

## 2. 目視と機械の役割分担

- **目視（Read）= 質的判断**: フックが刺さるか、トーンが揃っているか、視線誘導、写真と文字の馴染み。
- **機械（Python）= 量的判断**: 数値で白黒つくものは決定的計算に落とす。
  - WCAG コントラスト比: sRGB ガンマ解除 → 相対輝度 → 比率。AA 基準は通常文字 4.5:1、大文字 3:1。
    `wcag-contrast-ratio` パッケージあり。**生成後の画像解析より、生成前に spec/brand 色で
    検証する方が速い**。
  - はみ出し: `draw.textbbox()` / `Image.getbbox()` で bbox を取り、セーフ矩形との包含判定。
  - セーフゾーン侵犯: 端の帯領域の情報密度（画素 std 等）で検出。
  - before/after 比較: `pixelmatch` / SSIM。VLM をピクセル diff の主エンジンにしない
    （決定的 diff の上に VLM をトリアージ層として重ねるのが主流構成）。
- 機械チェックは **hard-fail（非ゼロ終了）** にしてパイプラインに組み込む。
  「spec に背景がない → 即 fail」のように、目視の前に弾けるものは spec レベルの制約に落とす。

## 3. レビュー精度を上げる構成

### コンタクトシート
複数スライドを1枚のグリッド画像（セーフゾーン枠を重ね描き）にまとめ、1回の Read で
シリーズ全体を俯瞰する。単体を1枚ずつ見るより「シリーズとしての一貫性」の欠陥
（トーン・ジャンプ率のばらつき）を発見しやすく、コンテキストコストも小さい。
※ ただし縮小により細部は読めない → §1 の拡大クロップと併用。

### フレッシュコンテキストでの敵対的レビュー
生成した本人セッションの自己採点は甘くなる（trust-then-verify gap）。重要な成果物は
別サブエージェントに「成果物＋判断基準（デザイン規範ファイル）」だけを渡し、
「スタイルの好みではなく、基準との不一致だけを報告して」と敵対的にレビューさせる。

### 多視点は並列に分ける
1エージェントに「コントラストも整列もブランド一貫性も同時に見て」と頼むと各観点が
浅くなる。観点ごとにサブエージェントを並列起動して統合する方が精度が高い。

### 証拠を見せる
「直しました」で終わらせず、修正後の画像/QA出力そのものを提示する。
1プロンプト内で「生成して、チェックして、直すところまで」を完結させると往復が減る。

## 4. 知識の蓄積（メモリ化）と spec 駆動

- **確定指摘の蓄積**: ユーザーが確定させたデザイン指摘は永続ファイルに追記し「一般原則より
  優先」で毎回読ませる（このリポジトリでは carousel-craft の `DESIGN_NOTES.md` が該当）。
  好みは一般原則から導出できないため、明示的に永続化しないと失われる。
- **spec(JSON) 駆動**: デザインを中間表現の spec として書き、決定的なレンダラに渡す。
  「創造的生成（コンセプト決定）」と「決定的処理（配置計算・フォント適用）」が分離され、
  後者を機械チェック・自動修正できる。プロンプト一発生成より再現性・デバッグ性が高い。
  学術的にも「LLM が spec 生成 → 決定的レンダリング → VLM レビュー → 修正ループ」の
  パイプラインが提案されている（GameUIAgent 等）。
- **プロンプト順序**: 画像はテキスト指示より前に置く方が精度が良い。

---

## 5. 典型ループ（テンプレート）

```
1. spec(JSON) を書く／更新する
2. 生成前チェック: spec 妥当性・色コントラストを機械検証（fail なら spec へ戻る）
3. レンダリング
4. 機械QA: はみ出し・セーフゾーン・密度 → hard-fail なら spec/コードへ戻る
5. 目視: コンタクトシートで俯瞰 + 重要細部の拡大クロップを Read
6. （重要案件）別サブエージェントで敵対的レビュー
7. 指摘が出たら 1 に戻る。ユーザーの確定指摘はデザインノートへ追記
```
