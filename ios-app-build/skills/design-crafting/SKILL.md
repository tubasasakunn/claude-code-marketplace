# DESIGN.md 作成支援 (design-crafting)

## 概要

「おしゃれにして」という曖昧な指示ではデザインは成立しない。色・形・タイポグラフィ・モチーフ・モーション・画面ごとのムードという複数の観点を、そのアプリの**コンセプトから一貫して導出**し、実装可能な仕様書として書き切るための実践ワークフロー。

このスキルが扱うのは2つのドキュメントの関係である。

- **`${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md`**（app-builder直下）— アプリを問わず反復する不変の基礎嗜好（紙と墨・フラット＋ヘアライン・反転選択・収まる動き等）。いわば「文法」。
- **`DESIGN.md`**（`Idea/ddd_アプリ名/`配下、このスキルの成果物）— そのアプリだけの固有の意匠（アクセント色・世界観・モチーフ・シグネチャ要素）。いわば「語彙」。

DESIGN.md は ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md を継承しつつ、`CONCEPT.md`（コンセプト・コア体験・機能要件）から固有の語彙を導出したものでなければならない。他アプリの意匠を使い回さず、かつ DESIGN_BASE の文法を破らない——この両立がこのスキルのゴールである。

## 全体ワークフロー

基本は上から順に進める。前工程の成果物（核メタファー・アクセントの意味づけ・形容詞3つ）を後工程の材料として持ち込む一直線の制作プロセス。

1. **[00-overview.md](chapters/00-overview.md)** — 序章。なぜ曖昧な指示が失敗するか、${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md と DESIGN.md の関係、8ステップの全体像。最初に読むべき索引。
2. **[01-translate-concept.md](chapters/01-translate-concept.md)** — 第1章: コンセプトを「翻訳」する。CONCEPT.md の核メタファー・動詞・身体感覚を洗い出し、色/形/動きの種を取り出す。以降すべての工程の起点。
3. **[02-color.md](chapters/02-color.md)** — 第2章: カラー設計。DESIGN_BASE のトークンを継承しつつ、固有のアクセントを注入する。配色理論とカラー役割の網羅チェック。
4. **[03-typography-motif.md](chapters/03-typography-motif.md)** — 第3章: タイポグラフィ方針とモチーフ（図形言語）。核メタファーを文字と形に変換する。
5. **[04-motion-signature.md](chapters/04-motion-signature.md)** — 第4章: モーション原則と「シグネチャ要素」設計。1画面1箇所の遊びをどこに置くか。
6. **[05-screens-states.md](chapters/05-screens-states.md)** — 第5章: 画面ごとのムード指定、コンポーネント状態の網羅、アクセシビリティ数値基準。
7. **[06-icon.md](chapters/06-icon.md)** — 第6章: AppIcon の方向性。モチーフを1つの図形に凝縮する。
8. **[07-artifact-review.md](chapters/07-artifact-review.md)** — 第7章: アーティファクトでユーザーと相談しながら確定し、DESIGN.md として書き出す。DESIGN.md のテンプレート構成もここにある。

補助資料:
- **[FAQ.md](FAQ.md)** — 判断に迷いやすいポイント（アクセント固定か可変か、serif をどこに差すか、DESIGN_BASE と衝突したときの扱い等）。
- **[CHECKLIST.md](CHECKLIST.md)** — 全工程を横断した最終診断リスト。DESIGN.md を完成として提示する前の最終ゲート。

## どの章を参照すべきか(診断表)

| ユーザー・作業の状態 | 参照する章 |
|:---|:---|
| CONCEPT.md はあるが、そこから何を意匠に翻訳すればいいか分からない | 00 → 01 |
| コンセプトの核メタファーは見えたが、色が決まらない | 02 |
| 色は決まったが、フォント・モチーフの手がかりがない | 03 |
| 静的な見た目は決まったが、動き（モーション）や「らしさの一瞬」がない | 04 |
| 全体トーンは決まったが、画面ごとの温度差や状態（disabled/empty等）が未整理 | 05 |
| 意匠は固まったが AppIcon の方向性がない | 06 |
| 各要素は揃ったが、まだ文書化・ユーザーレビューをしていない | 07 |
| DESIGN_BASE の原則と、そのアプリ固有の要求が矛盾している | FAQ.md |

## 使い方の原則

- **一緒に手を動かす場であって、要約を読ませる場ではない。** 各章の解説をそのまま語るのではなく、CONCEPT.md の実際の文言を材料に、その場で色・形・動きを一緒に決めていく。
- **前工程の成果物を次工程の材料にする。** 第1章で決めた「核メタファー」「アクセントの意味づけ」「形容詞3つ」を、以降すべての章で参照し続ける。行き当たりばったりに色やフォントを選ばない。
- **迷ったら ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md の原則に戻る。** 「紙と墨」「フラット＋ヘアライン」「反転選択」「収まる動き」の4原則は全工程に共通する判断軸になる。DESIGN_BASE を逸脱する提案をするときは、その逸脱がコンセプト上どうしても必要な理由を明文化する（[FAQ.md](FAQ.md) 参照）。
- **DESIGN.md が完成したと思ったら [CHECKLIST.md](CHECKLIST.md) で最終確認する。**
- **最終確定は必ずアーティファクトでのビジュアルプレビューを介す。** 文章だけで色や形を確定させない。第7章のプロセスに従い、Artifact ツールを使う前に `artifact-design` スキルを読み込むこと。

## 出典について

各章の内容は、以下を統合して再構成したものである。

- `${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md`（app-builder直下、ユーザー自身の過去アプリ4本の実測調査に基づく基礎嗜好）
- Qiita記事「AIでおしゃれな画面を作るためのデザインシステム学習ガイド」の骨子（デザインを戦略層〜統合層のピラミッドで捉える考え方、カラー役割・コンポーネント状態・トーン&マナーの網羅的分類）。ただしこの記事はWebデザイン中心のため、レスポンシブ対応やページ構成などiOSネイティブアプリに無関係な部分は取り込んでいない。
- `ui-ux-pro-max` / `frontend-design` スキル由来の、プラットフォーム非依存な一般理論（3層トークン設計、配色調和理論、Type Scale・Weight階層、Apple HIG準拠のモーション原則、タッチ・アクセシビリティの数値基準）。これらのスキルのWeb/React専用部分（shadcn/ui・Tailwind・CSS変数・レスポンシブブレークポイント等）は取り込んでいない。
