# 序章: なぜ「DESIGN.md」が必要なのか

## この教材の前提

「おしゃれにしてください」というAIへの指示は、それだけでは絶対に成立しない。Webデザインを分解した先行研究（本スキルの元になったQiita記事）は、デザインには情報順序・レイアウト・雰囲気・色・文字・部品・状態・余白・角丸・影・アクセシビリティ……という複数の観点があり、どれも単一の審美基準では決まらないと指摘する。同じアプリでも高齢者向け・若い女性向け・企業向けでは全く違う見た目が正解になる。**デザインの「正解」は、常にそのアプリのコンセプトとターゲットに依存する。**

この依存関係を無視してAIにデザインを丸投げすると、次の3パターンのどれかに落ちる。

1. **無難なテンプレート**: どこかで見たようなカード+シャドウ+丸角。コンセプトが何も反映されていない。
2. **過剰装飾**: グラデーション・グロー・グラスモーフィズムを理由なく積む「AIっぽい」画面。
3. **基礎からの逸脱**: 過去に決めた自分の好み（${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md）を毎回ゼロから作り直し、アプリごとに一貫性のない量産になる。

このスキルは、この3つの失敗をどちらも避けるための型を提供する。**基礎は使い回し、意匠だけをコンセプトから毎回導出する。**

## ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md と DESIGN.md の関係

app-builder パイプラインには2段のデザイン文書がある。

- **${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md**（不変・app-builder直下・全アプリ共通）: 過去アプリの実測から抽出した「毎回無意識にそうしていた共通項」。紙と墨の配色、フラット＋ヘアライン、反転選択、収まる動き。ここに書かれた原則は、新しいアプリだからといって毎回作り直さない。
- **DESIGN.md**（可変・`Idea/ddd_アプリ名/`配下・アプリ固有・このスキルの成果物）: そのアプリだけのアクセント色・世界観・モチーフ・シグネチャ要素。DESIGN_BASE を土台にしつつ、CONCEPT.md のコンセプトから固有の語彙を導出したもの。

比喩で言えば、${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md は「文法」、DESIGN.md は「その文章だけの語彙・言い回し」である。文法を守りながら、語彙だけを毎回コンセプトから起こす。過去アプリの固有意匠（特定パレット・特定キャラクター・特定モチーフ）を新アプリに引きずらないことも同じくらい重要——${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md 自身が「特定アプリ固有の意匠は意図的に書かない」と明言している。

## 8ステップの全体像

```
Input:  CONCEPT.md（コンセプト・コア体験・機能要件・ターゲット）
        ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md（不変の基礎トークンと原則）
          │
          ▼
1. 翻訳    コンセプトの核メタファー・動詞・身体感覚を洗い出す (01)
2. 色      DESIGN_BASE継承 + 固有アクセントの注入 (02)
3. 文字/形 タイポグラフィ方針 + モチーフ(図形言語) (03)
4. 動き    モーション原則 + シグネチャ要素(1画面1箇所の遊び) (04)
5. 画面    画面ごとのムード + 状態網羅 + アクセシビリティ (05)
6. Icon    AppIconの方向性 (06)
7. 確定    アーティファクトでレビュー → DESIGN.md書き出し (07)
          │
          ▼
Output: Idea/ddd_アプリ名/DESIGN.md
```

各ステップは前工程の答えを引き継ぐ直列プロセスである。第1章で決めた核メタファー・アクセントの意味づけ・形容詞3つを飛ばして色やフォントだけを単独で決めない。

## このスキル全体の使い方

Claude Codeがユーザーとアプリの見た目を決める会話をする際は、以下の順序で `chapters/` を参照する。

1. **CONCEPT.md と ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md を両方読み込んでいるかを最初に確認する。** どちらか一方でも欠けていたら、まずそれを読む・作ることから始める（CONCEPT.md がまだ無ければ `Idea/` のアイデア出し工程に差し戻す）。
2. **ユーザー・作業がいまどの工程にいるかを見極める。** SKILL.md の診断表を使い、該当する章から始める。ただし初回は第1章（核メタファーの翻訳）を飛ばさない——ここが弱いと、以降の色・形・動きがすべて根拠のない思いつきになる。
3. **各章は独立した読み物ではなく、前工程の答えを材料として渡す前提で書かれている。** 第2章以降を参照するときは、第1章で出した核メタファー・アクセントの意味づけ・形容詞3つを必ず一緒に持ち込む。
4. **迷ったら ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md の4原則（紙と墨・フラット＋ヘアライン・反転選択・収まる動き）に立ち返る。** それでも判断がつかない場合は [FAQ.md](../FAQ.md) を参照する。
5. **本書の解説をそのまま語るのではなく、実際に手を動かす方向に誘導する。** ユーザーの実際のコンセプト（例:「水に流す」「終わらせなくていい」等の言葉）を材料に、その場で色相・角丸・モーション時間を一緒に決めていく。
6. **最終的な確定は必ずアーティファクトでのビジュアルプレビューを介する。** 文章の記述だけでユーザーの合意を取らない。第7章のプロセスに従う。
7. **DESIGN.md が完成したら [CHECKLIST.md](../CHECKLIST.md) で最終確認してから提示する。**
