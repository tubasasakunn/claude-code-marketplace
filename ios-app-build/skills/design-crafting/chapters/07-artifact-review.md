# 第7章: アーティファクトでのレビューと DESIGN.md の書き出し

## ねらい

第1〜6章で決めた色・タイポ・モチーフ・モーション・画面ムード・AppIconの方向性を、文章だけで確定させず、ビジュアルプレビューを介してユーザーと確認する。合意が取れたら `Idea/ddd_アプリ名/DESIGN.md` として書き出す。

## コアフレームワーク

### Artifact を使う前に必ず `artifact-design` スキルを読み込む

Artifactツールでビジュアルプレビューを作る前に、必ず `artifact-design` スキルを Skill ツールで読み込み、そのガイダンスに従ってページを構成する。本章はその上に乗る「デザインレビュー用プレビュー」に特化した指針を追加するものであり、`artifact-design` スキル自体の代わりにはならない。

### プレビューに含めるべき要素

1. **カラースウォッチ**: 第2章で決めたライト/ダーク両方のトークンを、実際の色面として並べる。テキストとの組み合わせでコントラストも視認できるようにする。
2. **タイポグラフィサンプル**: 見出し・本文・serif箇所・mono箇所を実際のサイズ・weightで並べる。
3. **主要コンポーネント**: DESIGN_BASEの署名コンポーネント(反転チップ、フラットカード)にアプリ固有のアクセントを当てはめた実例。Default/Selected/Disabled等、第5章で洗い出した状態も並べる。
4. **モチーフの視覚化**: 第3章のモチーフを実際に線・面で描画したサンプル(SVGまたはCSS)。
5. **シグネチャ要素の説明**: 第4章の動きは静止画のプレビューでは伝わらないため、CSSアニメーションやモーションの疑似表現、または挙動を時系列の図解・文章で補足する。
6. **画面ムード一覧**: 第5章のムード表をそのまま視覚的な温度差(静か⇄主張してよい)が伝わる形で並べる。
7. **AppIconの方向性**: 第6章のレイヤー構成を簡易的に再現したサンプル。

このプレビューはSwiftUIそのものではなくHTML/CSSでの近似表現でよい。目的は実装コードを作ることではなく、色・形・動きの方向性についてユーザーと素早く合意を取ることである。

### ユーザーとの往復

- 1回で全部を完璧に当てるのではなく、**1〜2往復を目安**に調整する。「アクセントの彩度を落としてほしい」「serifの箇所を変えたい」等、具体的な指摘を歓迎する。
- ユーザーからのフィードバックが第1章の核メタファーや形容詞3つと矛盾する場合(例: 「静謐」と決めたのに派手な演出を求められる)、その矛盾を指摘した上でどちらを優先するか確認する。核メタファー自体を変える判断もありうる。

### DESIGN.md のテンプレート構成

合意が取れたら、以下の構成で `Idea/ddd_アプリ名/DESIGN.md` に書き出す(Nagasuの実例をテンプレート化したもの)。

```markdown
# {アプリ名} — DESIGN.md

> ${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md（紙と墨・フラット＋ヘアライン・反転選択・収まる動き）に準拠。
> ここに書くのは {アプリ名} 固有の意匠のみ。

## 0. 一行で
（核メタファーを1〜2文で。第1章の成果物）

## 1. カラーパレット
（ライトモード表・ダークモード表。アクセントを決めるものの説明。第2章の成果物）

## 2. 世界観・トーン
（形容詞3つとその説明、トーンの逆側=やらないこと。第1章の成果物）

## 3. タイポグラフィ方針
（serif/monoを差す場所。第3章の成果物）

## 4. モチーフ（図形言語）
（1〜3個のモチーフと用途の対応。第3章の成果物）

## 5. シグネチャ要素:「{名前}」
（挙動・所要時間・ハプティクス・reduceMotion時の簡略版。第4章の成果物）

## 6. AppIcon の方向性
（レイヤー構成、ダークモード対応。第6章の成果物）

## 7. 画面ごとのムード指定
（画面×ムード×補足の表。第5章の成果物）

## 8. 実装メモ
（DESIGN_BASE継承事項の再掲、トークン拡張の指示）
```

## 実践ステップ

1. `artifact-design` スキルを読み込む。
2. 第1〜6章の成果物をもとに、上記7要素を含むHTMLプレビューを作成し、Artifactツールで公開する。
3. ユーザーにプレビューを確認してもらい、フィードバックを反映して1〜2往復調整する。
4. 合意が取れたら、テンプレート構成に従って `Idea/ddd_アプリ名/DESIGN.md` を書き出す。
5. `adversarial-panel` スキルで敵対的レビューにかける。DESIGN_BASEの文法を破っていないか、他アプリの意匠の使い回しになっていないか、コンセプトから本当に一貫して導出されているかを独立した視点で検証する。
6. [CHECKLIST.md](../CHECKLIST.md) で最終確認し、ユーザーに完成を報告する。

## Claudeが使うときの適用ガイド

- プレビューを作る前に必ず `artifact-design` スキルをロードする手順を飛ばさない。
- ユーザーがプレビューを見て「なんか違う」とだけ言った場合、どの要素(色/形/動き/temperature)が引っかかっているのかを1つずつ確認する。漠然とした違和感を、第1〜6章のどの決定事項に紐づくか特定してから修正する。
- DESIGN.md を書き出したら、ファイルパスとともにユーザーに完成を伝え、次工程(セットアップスキルでのTokens実装、AppIcon生成)への接続を一言案内する。
