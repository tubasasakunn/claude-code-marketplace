# 第2章: カラー設計

## ねらい

${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md の背景・墨・階段トークンをそのまま継承し、第1章で決めた「何がアクセントを決めるか」の規則に従って、そのアプリ固有のアクセント色を注入する。色数を絞り、役割を漏れなく定義し、ライト/ダーク両方をこの章で確定させる。

## コアフレームワーク

### 継承する部分・変える部分

${CLAUDE_PLUGIN_ROOT}/skills/design-crafting/DESIGN_BASE.md から**そのまま継承する**（アプリごとに作り直さない）:
- 背景（紙）: クリーム系オフホワイト帯域。純白は使わない。
- テキスト（墨）: 暖色寄りの墨色。副次テキストは暖色グレー。
- ヘアライン: 墨色の低opacity。
- 余白・角丸・影の階段。

**そのアプリだけで決める**:
- アクセント色（第1章の規則に従い1〜2色）とその半透明バリエーション。
- アクセントが担う固有の意味（Nagasu の「まだ流していない/もう流した」のような二項対立、あるいは単なる装飾か）。

### 配色調和理論でアクセントの根拠を作る

「なんとなく良さそうな色」を避けるため、以下のいずれかの調和関係でアクセントの色相を選ぶ。

- **単色相（Monochromatic）**: 墨色と同系統の濃淡だけで構成。最も静かで DESIGN_BASE の「紙と墨」思想に近い。
- **類似色（Analogous）**: 背景・墨の暖色帯域に隣接する色相（テラコッタ→アンバー等）。馴染みやすく、DESIGN_BASE が好むアース・暖色・くすみ系との親和性が高い。
- **補色（Complementary）**: 暖色の紙に対し寒色寄り（くすみティール、インディゴ等）を1色だけ差す。Nagasu の水色はこの関係にあたり、コントラストで意味を強調したいときに使う。
- **三色配色（Triadic）**: 複数カテゴリを色分けする必要があるアプリ（タグ・カテゴリ管理系）でのみ検討する。ビビッドにせず、必ず彩度を落として紙の上に馴染ませる。

彩度はいずれの場合も DESIGN_BASE の「ビビッドな原色をブランド色として据えることはしない」を必ず守る。

### カラー役割を漏れなく定義する

Web向けの一般的なカラーシステム（Primary/Secondary/Accent/Background/Foreground/Muted/Border/Destructive 等の「役割＋On色（前景とのペア）」定義）を、iOSのセマンティックカラーの語彙に翻訳して漏れをチェックする。DESIGN_BASE + アプリ固有トークンで、最低限このロールが埋まっているか確認する。

| 役割 | DESIGN_BASE / DESIGN.md 側の対応 | 備考 |
|---|---|---|
| Background | `background`（紙） | 継承 |
| Surface/Card | `card` | 継承 |
| Text Primary | `textPrimary`（墨） | 継承 |
| Text Secondary | `textSecondary` | 継承 |
| Border | `hairline` | 継承 |
| Accent | `accent◯◯`（固有） | 第1章の規則に従い注入 |
| Accent Soft | `accent◯◯Soft`（opacity 0.1〜0.3） | DESIGN_BASE の「色付き半透明タグ」パターン |
| Success / Warning / Error | 必要なアプリのみ追加 | ほとんどのミニマルなアプリでは不要。トースト・バリデーションが必要な場合のみ、彩度を落とした赤・緑を1段だけ定義する |

Success/Warning/Error を安易に「賑やかしい原色」で足さないこと。DESIGN_BASE の彩度方針に合わせ、くすみ系で統一する。

### ライト/ダーク両方をこの章で決める

Nagasu の DESIGN.md のように、ライトモード・ダークモードそれぞれのテーブルをこの時点で作る。ダーク面は「無彩の黒でなく、暖色に寄せた焦茶〜墨の暗色」という DESIGN_BASE 原則を守り、アクセントは暗所での視認性のために明度を上げる（Nagasu では `#4C7A75` → `#7FB3AC` のように明るくしている）。

### トークン経由を徹底する

色は必ずセマンティックトークン（`Tokens.Colors.accentWater` 等）経由で定義する。hex 直書きを許可しない。この原則は DESIGN.md 本文にも実装メモとして明記する。

## 実践ステップ

1. DESIGN_BASE の継承トークン（background/card/textPrimary/textSecondary/hairline）をそのまま表に転記する。
2. 第1章の「アクセントを決める規則」に従い、アクセントの色相を配色調和理論（単色相/類似色/補色/三色配色）のどれで選ぶか決める。
3. アクセントの hex 値をライト/ダーク両方で決める（ダークは明度を上げる）。
4. アクセントの半透明バリエーション（Soft、opacity 0.1〜0.3）を追加する。
5. Success/Warning/Error が本当に必要か検討する。不要なら「使わない」と明記して省略する。
6. すべての色をトークン名（`Tokens.Colors.xxx`）として一覧表にまとめる。

## チェックリスト

- [ ] 純白・純黒を使っていないか
- [ ] アクセントの選定根拠（どの配色調和関係か）が説明できるか
- [ ] アクセントがビビッドな原色になっていないか（彩度を落としているか）
- [ ] ライトモード・ダークモード両方のテーブルがあるか
- [ ] ダークモードのアクセントは明度を上げて視認性を確保しているか
- [ ] 半透明タグ用の Soft バリエーションがあるか
- [ ] Success/Warning/Error は本当に必要な場合のみ追加し、彩度を落としているか
- [ ] すべて `Tokens.Colors.xxx` のようなセマンティックトークン名で書かれているか（hex直書きの提案になっていないか）

## Claudeが使うときの適用ガイド

- ユーザーがいきなり「青系がいい」のように色相だけ指定してきたら、それが第1章の核メタファーとどうつながるかを確認する。つながらない場合は「その青は、コンセプトの何を象徴しますか？」と問い返す。
- Success/Warning/Error を機械的に足そうとしたら、「このアプリにバリデーションエラーやトースト通知は本当にありますか？」と確認し、不要なら省略するよう促す（DESIGN_BASE のミニマル志向を守るため）。
- ダークモードを後回しにしようとしたら、この章の時点でライト/ダーク両方を確定させる（後の章のプレビューや実装で手戻りが起きるため）。
