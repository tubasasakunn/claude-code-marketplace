# 第4章: モーション原則と「シグネチャ要素」

## ねらい

DESIGN_BASE のモーション原則（「弾む」より「収まる」）を継承しつつ、そのアプリの核メタファーが最も強く現れる「1画面1箇所の遊び」＝シグネチャ要素を設計する。全体を静かに保ったまま、コア体験の瞬間だけ意匠が主張してよいという DESIGN_BASE の構成の癖を実装に落とし込む章。

## コアフレームワーク

### 継承するモーション原則

- spring は `response 0.3〜0.5, dampingFraction 0.7〜0.85`。dampingFraction を 0.7 未満にしない（弾ませすぎない）。
- ボタン押下は `easeOut(duration: 0.18〜0.2)` ＋ `scaleEffect 0.92〜0.96`。
- 演出的な遅延アニメ（シグネチャ要素等）だけは `easeInOut(1.0〜1.5) + delay` を許容する特例枠。
- `@Environment(\.accessibilityReduceMotion)` 対応を全アニメーション箇所で徹底する（`reduceMotion ? nil : animation` パターン）。reduceMotion 時の簡略版を持たないモーションは実装漏れとみなす。

### Apple HIG 準拠の補助原則(プラットフォーム非依存の一般理論から)

DESIGN_BASE には明記されていないが、Apple の標準的なモーション設計原則として以下を判断の補助線にしてよい。

- **時間の目安**: 一般的なUIトランジションは150〜300ms。DESIGN_BASE の帯域(0.18〜0.5秒)とほぼ整合する。
- **Exit < Enter**: 消える動きは現れる動きより短くする。要素が去るときにユーザーを待たせない。
- **hierarchy motion**: 階層の深い画面遷移ほど、下から出現する・大きく見せるなど「奥から手前へ」の動きを使う。逆に同階層の切り替え（タブ等)はクロスフェード等、階層を主張しない動きにする。

### シグネチャ要素の設計

DESIGN_BASE 6章「1点だけの遊び」の実装がこの章の中心である。

1. **置き場所を1箇所に絞る**: コア体験（CONCEPT.mdの「コア体験3行」）の中で、最もそのアプリらしい瞬間を1つ選ぶ。他の画面は装飾ゼロに保つ。
2. **核メタファーをそのまま動きに翻訳する**: Nagasu の例では「紙片が水面に触れ、波紋が広がりながら薄れて消える」——核メタファー(水に流す)をそのままアニメーションの物理的挙動として再現している。比喩の飾り付けではなく、比喩そのものが動きになっている状態を目指す。
3. **所要時間・ハプティクスまで仕様化する**: 「1.2〜1.6秒」「触れる瞬間に `.light` ハプティクス1回」のように、後で実装者（未来の自分やAI）が再現できる精度まで書く。
4. **reduceMotion時の簡略版を必ず設計する**: 波紋なしでフェードのみ、等。シグネチャ要素ほど作り込みたくなるが、アクセシビリティの例外にしない。
5. **他画面への流用を禁止する**: シグネチャ要素はそのアプリの「特別な瞬間」なので、他の一覧画面や設定画面には持ち込まない。持ち込むと「1点だけの遊び」が「あちこちにある遊び」に薄まる。

## 実践ステップ

1. CONCEPT.mdのコア体験(3行)から、最もアプリらしい瞬間を1つ選ぶ。
2. 第1章の核メタファーを、その瞬間の具体的な動き(何が・どこから・どこへ・どう変化して消えるか)に翻訳する。
3. 所要時間・イージング・ハプティクスのタイミングを数値で仕様化する。
4. reduceMotion時の簡略版を設計する。
5. このシグネチャ要素を使わない画面(一覧・設定・詳細等)を明示的にリストアップし、「完全に静的に保つ」と明記する。

## Claudeが使うときの適用ガイド

- ユーザーが複数の画面に凝ったアニメーションを入れたがったら、DESIGN_BASE の「1点だけの遊び」原則を伝え、「アプリ全体で一番"らしさ"が出る瞬間はどこですか、そこ以外は静かに保ちましょう」と絞り込みを促す。
- シグネチャ要素の動きが抽象的(「気持ちよく光る」等)にとどまっている場合、「その光り方は、コンセプトの何を表していますか。具体的に何がどこからどこへ動きますか」と、核メタファーへの翻訳を掘り下げる。
- reduceMotion対応が漏れていたら、DESIGN_BASE 5章の徹底事項として必ず思い出させる。
